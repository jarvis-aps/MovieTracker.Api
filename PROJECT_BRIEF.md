## Цель

Не просто получить готовое приложение, а разобраться в современной backend/frontend разработке на практике: EF Core, ASP.NET Core, модульная архитектура, контейнеризация, распределённый деплой — и параллельно выработать рабочий процесс с ИИ-агентами, при котором понимание кода не теряется.

Приложение: трекер просмотренных фильмов. Стартует с одной таблицы (`Movies`: название + статус), дальше растёт по сложности данных, бэкенда, фронта и инфраструктуры — четырьмя отдельными, не обязательно синхронными осями.

## Стек

- **.NET 10** — не 9. .NET 8 и .NET 9 теряют поддержку Microsoft 10 ноября 2026, актуальный LTS — десятка, поддержка до ноября 2028.
- **EF Core** + PostgreSQL (пакет Npgsql.EntityFrameworkCore.PostgreSQL)

MediatR ушёл на коммерческую лицензию в 2025-м (бесплатная Community-редакция для индивидуальных разработчиков и компаний с доходом до $5 млн — для пет-проекта не проблема), но раз цель этого проекта — понимание, а не готовое решение, разумная альтернатива — написать свой мини-mediator на 20-30 строк.
- **React + TypeScript** на фронте — но не с первого этапа. Этап 1 обходится без стейт-менеджера вообще.

## Философия проекта

1. **Сложность вводится по необходимости, а не заранее.** Модульный монолит, CQRS, слои — появляются, когда есть реальный повод (второй домен, вторая сущность, реальная бизнес-логика), а не потому что "так принято". Архитектура, добавленная без повода, — тот же нейро-слоп, только не от агента, а от преждевременного дизайна.
2. **Данные / бэкенд / фронт / инфраструктура — четыре независимые оси.** Не обязаны расти синхронно. Можно контейнеризировать рано, если хочется пощупать пораньше, или задержаться на локальном стенде, если фокус пока на бэке.
3. **Понимание — приоритет номер один.** Важнее скорости и важнее "правильной" архитектуры с первого раза.

## Режим работы агента: наставник, а не исполнитель

Это обязательное правило работы для любого агента (Claude Code, Claude в чате или другой), который работает по этому брифу — не рекомендация.

### Этап 1 — строгий режим

- Агент **не пишет реализацию** за пользователя.
- На каждую задачу агент выдаёт: **цель** (что это должно объяснить или натренировать), **чек-лист шагов**, **критерий готовности**. Формат — см. ниже.
- Пользователь реализует сам.
- Агент проверяет результат (код, вывод, поведение), указывает на конкретные проблемы и задаёт наводящие вопросы — не переписывает молча.
- Если пользователь застрял — агент может показать короткий (1-3 строки) фрагмент-подсказку, но обязан объяснить, почему именно так, а не просто вставить рабочий код.
- Задачи выдаются **по одной**, не все сразу.

### Этап 2+ — частичное послабление

Разрешено делегировать агенту:
- миграции EF Core
- DTO-мапинг
- повторяющийся CRUD-boilerplate **по уже установленному пользователем паттерну**

Не разрешено делегировать никогда (в том числе на этапах 4-5):
- границы модулей и что уходит в событие / что в прямой вызов
- дизайн модели данных
- дизайн запросов и их сложность

Для делегированных кусков агент всё равно кратко объясняет, что сделал, если пользователь не знаком с деталью реализации.

### Задача 1.4: PATCH /movies/{id}/status — ✅ ЗАКРЫТА
**Цель:** первый write-эндпоинт
**Шаги:**
- [x] Minimal API endpoint `PATCH /movies/{id}/status`
- [x] Обновление через DbContext, SaveChanges
- [x] Обработка кейса "фильм не найден" (404)
- [x] Проверить через curl/Postman
**Проверка себя:** статус меняется в БД, повторный GET показывает изменение.

> По ходу задачи: (1) новый статус передаётся через query-параметр (`?status=Watched`) — параметр `Status status` в хендлере ASP.NET Core сам биндит из query string по конвенции (любой тип с `TryParse`, включая enum, без атрибута `[FromQuery]`); отсутствие параметра само по себе даёт 400 с понятным сообщением; (2) была путаница между "найти фильм" (внутренний шаг сервера через `FirstOrDefaultAsync`, нужен для change tracking) и "узнать статус" (это уже закрыто в `GET /movies`) — важно: PATCH это один запрос с двумя данными сразу (`id` из пути + новый статус из query), не два отдельных эндпоинта; (3) сквозная проверка — успешный патч (200, реально меняет `Status` в Postgres), 404 на несуществующий id, 400 без обязательного параметра. Мелкий незакрытый нюанс: `SaveChanges()` синхронный внутри async-хендлера (стилистически лучше `SaveChangesAsync()`, не блокирует задачу).

**Реальные баги, найденные и исправленные пользователем самостоятельно по ходу ревью (не агентом):**
1. Первая версия читала `title`/`status` из query-string, а не из тела — не соответствовало критерию. Поправлено на DTO (`NewMovie newMovie` параметром), подтверждено эмпирически (тело реально стало читаться, а не игнорироваться).
2. Побочно всплыла разница между биндингом enum из route/query (`TryParse`, принимает имя типа `"Watched"`) и из JSON-тела (`System.Text.Json`, по умолчанию — число, не имя) — не баг, а особенность двух разных механизмов ASP.NET Core, зафиксирована для памяти.
3. Конструктор `Movie(string title, Status status)` не присваивал `Status = status` — все фильмы через `POST` создавались с дефолтным `Status.Watched` независимо от запроса. Найдено эмпирически (в БД оказывалось не то значение, что просили), исправлено.
4. `Results.Created($"/movies/{movie.Title}", ...)` — использование `Title` вместо `Id` в URL реально **уронило приложение с 500** (кириллица в HTTP-заголовке `Location` — недопустимый символ вне ASCII). Поправлено на `movie.Id` — заодно разобрали, почему ресурсы в REST адресуют по `Id`, а не по произвольному тексту.
5. В ответе возвращался `newMovie` (входной DTO, эхо запроса, без `Id`) вместо `movie` (реально сохранённая сущность) — маскировало баг №3 в самом ответе API. Поправлено на возврат `movie`.

Все пять пунктов пользователь нашёл и исправил сам после того, как агент показывал результат эмпирической проверки (curl + прямой запрос в БД) и объяснял, *почему* именно так — не давая готового кода.

## Как пользоваться этим документом

Файл кладётся в корень репозитория. Задачи выдаются по одной, не все сразу — прогресс идёт через цикл "задача → реализация → проверка → следующая задача". Детальные планы для этапов 2-5 составляются по этому же принципу, когда до них доходит очередь: заранее расписывать их означает планировать то, что ещё может измениться по ходу этапа 1.

После каждой закрытой задачи — обновляй раздел "Текущий статус" в начале файла (что сделано, что уточнилось по факту, какая задача следующая) и отмечай чек-листы галочками. Не оставляй его как есть: это единственное место, по которому можно понять, где именно остановилась работа, не пересказывая всю историю чата.

## Цель

Не просто получить готовое приложение, а разобраться в современной backend/frontend разработке на практике: EF Core, ASP.NET Core, модульная архитектура, контейнеризация, распределённый деплой — и параллельно выработать рабочий процесс с ИИ-агентами, при котором понимание кода не теряется.

Приложение: трекер просмотренных фильмов. Стартует с одной таблицы (`Movies`: название + статус), дальше растёт по сложности данных, бэкенда, фронта и инфраструктуры — четырьмя отдельными, не обязательно синхронными осями.

## Стек

- **.NET 10** — не 9. .NET 8 и .NET 9 теряют поддержку Microsoft 10 ноября 2026, актуальный LTS — десятка, поддержка до ноября 2028.
- **EF Core** + PostgreSQL (пакет Npgsql.EntityFrameworkCore.PostgreSQL)
- **Mediator-паттерн** — только с этапа 3, когда появятся модули. MediatR ушёл на коммерческую лицензию в 2025-м (бесплатная Community-редакция для индивидуальных разработчиков и компаний с доходом до $5 млн — для пет-проекта не проблема), но раз цель этого проекта — понимание, а не готовое решение, разумная альтернатива — написать свой мини-mediator на 20-30 строк.
- **React + TypeScript** на фронте — но не с первого этапа. Этап 1 обходится без стейт-менеджера вообще.

## Философия проекта

1. **Сложность вводится по необходимости, а не заранее.** Модульный монолит, CQRS, слои — появляются, когда есть реальный повод (второй домен, вторая сущность, реальная бизнес-логика), а не потому что "так принято". Архитектура, добавленная без повода, — тот же нейро-слоп, только не от агента, а от преждевременного дизайна.
2. **Данные / бэкенд / фронт / инфраструктура — четыре независимые оси.** Не обязаны расти синхронно. Можно контейнеризировать рано, если хочется пощупать пораньше, или задержаться на локальном стенде, если фокус пока на бэке.
3. **Понимание — приоритет номер один.** Важнее скорости и важнее "правильной" архитектуры с первого раза.

## Режим работы агента: наставник, а не исполнитель

Это обязательное правило работы для любого агента (Claude Code, Claude в чате или другой), который работает по этому брифу — не рекомендация.

### Этап 1 — строгий режим

- Агент **не пишет реализацию** за пользователя.
- На каждую задачу агент выдаёт: **цель** (что это должно объяснить или натренировать), **чек-лист шагов**, **критерий готовности**. Формат — см. ниже.
- Пользователь реализует сам.
- Агент проверяет результат (код, вывод, поведение), указывает на конкретные проблемы и задаёт наводящие вопросы — не переписывает молча.
- Если пользователь застрял — агент может показать короткий (1-3 строки) фрагмент-подсказку, но обязан объяснить, почему именно так, а не просто вставить рабочий код.
- Задачи выдаются **по одной**, не все сразу.

### Этап 2+ — частичное послабление

Разрешено делегировать агенту:
- миграции EF Core
- DTO-мапинг
- повторяющийся CRUD-boilerplate **по уже установленному пользователем паттерну**

**Актуально с начала этапа 2:** пользователь явно попросил не пользоваться этим послаблением по умолчанию. Подробный режим этапа 1 (детальные шаги + объяснение "почему так, а не иначе" на каждом шаге) остаётся включён, пока пользователь лично не отменит явным сообщением — не сокращать формат задач автоматически при смене этапа.

Не разрешено делегировать никогда (в том числе на этапах 4-5):
- границы модулей и что уходит в событие / что в прямой вызов
- дизайн модели данных
- дизайн запросов и их сложность

Для делегированных кусков агент всё равно кратко объясняет, что сделал, если пользователь не знаком с деталью реализации.

### Формат выдачи задачи

```
### Задача N.N: [название]
**Цель:** что это учит / зачем это нужно
**Шаги:**
- [ ] пункт
- [ ] пункт
**Проверка себя:** как понять, что задача сделана правильно
```

### Критерии перехода на следующий этап

- Пользователь может объяснить свой код своими словами, без агента.
- Минимум одна фича за этап сделана самостоятельно, без ИИ, за разумное время. Если тяжело — не двигаться дальше, закрепить текущий уровень.

## Дорожная карта

| Этап | Данные и запросы | Бэкенд | Фронт |
|---|---|---|---|
| 1. MVP | `Movies(Id, Title, Status)`. List, UpdateStatus | Один проект, Minimal API, DbContext напрямую в хендлере — без слоёв и mediator-паттерна | html+fetch или один React-компонент без стейт-менеджера |
| 2. Домен растёт | + Genre, Year, Rating, Notes, даты. Фильтр, сортировка, поиск, пагинация | Service-слой + DTO отдельно от EF-сущностей | Структура компонентов, React Query для серверного стейта |
| 3. Модульность | Связанные таблицы: Genres (M:N), Users (владение), Lists | Модульный монолит: модули Movies/Users/Lists с границами, CQRS (свой mediator или MediatR), общение через события | Роутинг, auth-экраны |
| 4. Зрелость | Агрегации, статистика, полнотекстовый поиск | Cross-cutting: валидация, auth, логирование | Графики, loading/error-стейты |
| 5. Опционально | История статусов (лог изменений), фоновые напоминания | Hosted background service, вынос одного модуля в отдельный сервис | Real-time через SignalR |

### Задача 1.4: PATCH /movies/{id}/status — ✅ ЗАКРЫТА
**Цель:** первый write-эндпоинт
**Шаги:**
- [x] Minimal API endpoint `PATCH /movies/{id}/status`
- [x] Обновление через DbContext, SaveChanges
- [x] Обработка кейса "фильм не найден" (404)
- [x] Проверить через curl/Postman
**Проверка себя:** статус меняется в БД, повторный GET показывает изменение.

> По ходу задачи: (1) новый статус передаётся через query-параметр (`?status=Watched`) — параметр `Status status` в хендлере ASP.NET Core сам биндит из query string по конвенции (любой тип с `TryParse`, включая enum, без атрибута `[FromQuery]`); отсутствие параметра само по себе даёт 400 с понятным сообщением; (2) была путаница между "найти фильм" (внутренний шаг сервера через `FirstOrDefaultAsync`, нужен для change tracking) и "узнать статус" (это уже закрыто в `GET /movies`) — важно: PATCH это один запрос с двумя данными сразу (`id` из пути + новый статус из query), не два отдельных эндпоинта; (3) сквозная проверка — успешный патч (200, реально меняет `Status` в Postgres), 404 на несуществующий id, 400 без обязательного параметра. Мелкий незакрытый нюанс: `SaveChanges()` синхронный внутри async-хендлера (стилистически лучше `SaveChangesAsync()`, не блокирует задачу).

Поправлено на `movie.Id` — заодно разобрали, почему ресурсы в REST адресуют по `Id`, а не по произвольному тексту.

**Цель:** спроектировать опциональные query-параметры фильтра и разобраться с `IQueryable` — условный `.Where(...)`, транслируемый в SQL и выполняемый в Postgres, а не в памяти после `ToListAsync()`.

- [x] `GET /movies` принимает необязательные `status` (`Status?`) и `genre` (`Genre?`)

- [x] Без фильтров — полный список, как раньше
- [x] Фильтр по `genre` — проверка вхождения в `List<Genre>` (`.Contains(...)`), не равенство
- [x] Маппинг в `MovieDto` — после `ToListAsync()`, на уже отфильтрованном результате

> По ходу задачи — три показательные ошибки первой попытки: (1) вместо одного эндпоинта с опциональными параметрами были заведены три отдельных `MapGet("/movies", ...)` — один без параметров, по одному на `status` и на `genre`; ASP.NET Core матчит маршрут по пути и HTTP-методу до какого-либо биндинга параметров, поэтому три идентичных по шаблону маршрута дают `AmbiguousMatchException` на любой запрос (компилятор предупреждает об этом сам, `warning ASP0022`), и вдобавок с раздельными эндпоинтами нет способа применить оба фильтра одним запросом — при росте числа независимых фильтров (следом идут сортировка/поиск/пагинация) число нужных комбинаций-эндпоинтов растёт как 2ⁿ; поправлено на один эндпоинт с `Status?`/`Genre?`; (2) первая версия фильтрации грузила `_context.Movies.ToListAsync()` **до** `.Where(...)` и фильтровала уже материализованный `List<Movie>`/`List<MovieDto>` в C# — на 3-5 тестовых записях разницы не видно, но это означает выкачивание всей таблицы по сети при каждом запросе вместо `WHERE` в самом SQL; поправлено на построение `IQueryable` и условный `.Where()` до `ToListAsync()`; (3) при живой проверке `?genre=Sport` вернул пустой список, хотя один из сидинг-фильмов явно содержал `Genre.Sport` — причина оказалась не в фильтре, а в данных: `Genre` хранится в Postgres как голое число (позиция в enum), а более ранняя правка того же дня (удаление дублей `Romance`/`Romantic`, `SciFi`/`ScienceFiction` из середины списка) сдвинула числовые коды всех элементов после них, и уже сохранённая в базе запись осталась с устаревшим числом, не соответствующим новому `Genre.Sport`; исправлено фиксацией явных числовых значений у всех членов `Genre` (`Action = 0, ...`) и пересидингом таблицы — зафиксировано на будущее: правка enum, уже используемого в БД, без явных значений тихо портит существующие данные.

### Задача 2.5: Сортировка `GET /movies` — ✅ ЗАКРЫТА
**Цель:** расширить `IQueryable`-паттерн из 2.4 (условный `.Where(...)`) на `.OrderBy(...)`/`.OrderByDescending(...)` — сортировка по полю и направлению, независимая от фильтров и совместимая с ними в одном запросе.

**Проверка себя:** curl по каждому полю в обоих направлениях, фильтр+сортировка одним запросом, `Rating` проверен на реально разных значениях (сидинговые записи были с одинаковым `Rating=0` — значения выставлены заранее через `PATCH /rating`, иначе порядок ничего не доказывает).

> По ходу задачи — несколько кругов путаницы, все показательные: (1) первая реакция — "нужен отдельный эндпоинт `/movies/sort`"; снята прямой аналогией с 2.4, где три отдельных `MapGet` под разные фильтры упали с `AmbiguousMatchException` и не давали скомбинировать фильтры одним запросом — сортировка, как и фильтр, это ещё один опциональный query-параметр на том же ресурсе, не новый путь; (2) попытка нащупать разницу "фильтр vs сортировка" через пример `rating=8` (точное совпадение) против `rating>8` (диапазон) — на деле оба варианта это фильтры (`WHERE`, сужение набора), различающиеся только оператором сравнения, не пример сортировки; настоящий критерий — сужает ли операция набор строк, или просто переставляет их местами (`ORDER BY`); (3) первая попытка диапазона использовала `.OrderBy(m => m.Rating >= minRating)` — булев предикат внутри `OrderBy` — ожидалось, что несовпадающие фильмы исчезнут из ответа; на деле `OrderBy` ничего не исключает, только переставляет; поймано эмпирически — подсчётом количества фильмов в ответе до и после параметра (не изменилось); (4) вторая попытка спрятала сортировку и `status`/`genre`-фильтры в `if`/`else`, завязанные на присутствие `minRating`, из-за чего фильтры и сортировка стали взаимоисключающими (фильтр переставал применяться при переданном `minRating`), а `maxRating` вообще перестал использоваться где-либо (мёртвый параметр, не выявленный сразу); (5) путаница о типе параметра "какое поле сортировать" — предлагалось использовать тот же `float? minRating` и для сортировки по `Rating`; прояснили, что выбор поля — это идентификатор поля (имя), не значение из домена конкретного поля, и такой параметр не подошёл бы для `Title` (`string`) или `Year` (`int`); решено через `enum SortBy` по тому же паттерну, что `Status?`/`Genre?` в 2.4 — даёт `400`-валидацию невалидных значений бесплатно, без лишнего кода; (6) направление сортировки — `bool? sortByDesc`, применяется как `sortByDesc is true ? OrderByDescending(...) : OrderBy(...)` внутри `switch` по `sortBy`; в отличие от фильтров, где независимые `.Where(...)` складываются друг с другом, здесь уместен именно `switch` — поле для сортировки взаимоисключающий выбор одного варианта, а не комбинация нескольких сразу.

> Отдельно — сортировка по `Genre` сознательно отложена: `Genres` — это `List<Genre>` (у фильма может быть несколько жанров), и "сортировать по жанру" неоднозначно в этом случае. Обсуждали вариант "фильм с хотя бы одним совпадающим с искомым жанром — выше в списке", но для этого нужен ещё один параметр (какой жанр считается "искомым"), неясно, как это соотносится с уже существующим `genre`-фильтром (тот уже сужает список только до фильмов с этим жанром — сортировать "по совпадению" внутри уже отфильтрованного списка бессмысленно), и не определён порядок внутри групп "совпало"/"не совпало". Решено не усложнять сейчас: `SortBy.Genre` остался в `enum`'е как no-op-заглушка (`case SortBy.Genre: case null: break;` в `switch`) — валидное значение параметра, которое ничего не делает, без сопроводительного комментария в коде (известный, принятый на этом этапе компромисс — не забыть при возврате к этой фиче).

### Задача 2.6: Пагинация `GET /movies` — ✅ ЗАКРЫТА
**Цель:** дополнить `IQueryable`-пайплайн (`.Where()` → `.OrderBy()`) операциями `.Skip()`/`.Take()`, и на практике увидеть разницу между поведением LINQ-to-Objects и LINQ-to-Entities на граничных значениях.

- [x] Дефолты `page ??= 1`, `pageSize ??= 10`, если не переданы — пагинация работает всегда, не ломая обратную совместимость (без параметров возвращаются все текущие записи, т.к. их меньше дефолтного `pageSize`)
- [x] `.Skip(...)`/`.Take(...)` — в конце пайплайна, после `.Where()` и `.OrderBy()`, перед `.ToListAsync()`
- [x] Валидация `page <= 0`/`pageSize <= 0` — своё исключение `InvalidPageSizeException` (по образцу `InvalidRatingException` из 2.3), поймано в хендлере, `400` с чистым сообщением
- [x] Пустой результат (фильтр ничего не нашёл, или страница за пределами данных) — `200` с `[]`, не `404`
**Проверка себя:** страницы не пересекаются и вместе покрывают весь список без пропусков; без параметров — поведение как раньше; `page=0`/отрицательные значения — `400`, не `500`; пустой список — `200`; пагинация комбинируется с фильтром и сортировкой одним запросом.

> По ходу задачи: (1) первая реализация задала `int? page`, но `int pageSize` (без `?`) в сигнатуре `Program.cs` — по той же конвенции биндинга ASP.NET Core, что уже фигурировала в 1.4, non-nullable value-type параметр без атрибута считается обязательным; в результате `GET /movies` без единого параметра стал давать `400 "Required parameter int pageSize was not provided"` — сломав обратную совместимость вообще всех предыдущих сценариев (2.1-2.5); исправлено на `int? pageSize`; (2) на вопрос "нужно ли валидировать `page`/`pageSize` <= 0" был дан не совсем верный совет — что `.Skip()`/`.Take()` с нулём/отрицательным числом в LINQ не бросают исключение; это верно только для LINQ-to-Objects (списков в памяти), но не для `IQueryable`, транслируемого в SQL — Postgres отказывается выполнять `OFFSET`/`LIMIT` с отрицательным значением и роняет `NpgsqlException`, долетающий как необработанный `500`; поймано эмпирически (тем же способом, что и раньше — реальным запросом, не чтением документации LINQ по памяти); (3) валидация `page`/`pageSize` изначально кинула переиспользованный `InvalidRatingException` — сработало технически, но название типа не отражало реальную причину ошибки (клиент получил бы правильное сообщение, но код ловил бы "рейтинг" там, где речь о пагинации); заведено отдельное `InvalidPageSizeException` по тому же паттерну; (4) `GET /movies` при пустом результате (фильтр ничего не нашёл, страница за пределами данных) сначала стал отдавать `404 Not Found` — попытка убрать мёртвую `null`-проверку (`List<MovieDto>` физически не может быть `null`, копия паттерна с `PATCH`, где `null` значит "не нашли по id") заменила её на `result.Count != 0 ? Ok() : NotFound()`; разобрали разницу между "конкретного ресурса по id не существует" (законный `404`, как в `PATCH /movies/{id}`) и "коллекция существует, просто ни один элемент не подошёл под фильтр" (законный `200` с пустым массивом) — решение о том, пуст список или нет, каждый раз остаётся за клиентом (фронтендом), не за HTTP-статусом; поправлено на безусловный `Results.Ok(result)`.

### Рефакторинг: `MovieQueryParameters` + `[AsParameters]` для `GET /movies` — ✅ ЗАКРЫТО
**Цель:** объединить шесть разрозненных query-параметров (`status`, `genre`, `sortBy`, `sortByDesc`, `page`, `pageSize`) в один объект, чтобы сигнатура `MapGet`/`GetMoviesAsync` не росла линейно с каждым новым модификатором запроса (следующий на очереди — поиск); знакомство с `[AsParameters]` — механизмом ASP.NET Core Minimal API, биндящим сразу несколько query-параметров в один объект одним атрибутом.
**Шаги:**
- [x] `Models/MovieQueryParameters.cs` — класс с primary constructor (`Status? status, Genre? genre, SortBy? sortBy, bool? sortByDesc, int? page, int? pageSize`), свойства инициализируются из параметров конструктора
- [x] `Program.cs` — `MapGet("/movies", ...)` принимает один параметр `[AsParameters] MovieQueryParameters movieQueryParameters` вместо шести отдельных
- [x] `MovieService.GetMoviesAsync(MovieQueryParameters movieQueryParameters)` — обращение к полям через `movieQueryParameters.Status` и т.д., сама логика (фильтр/сортировка/пагинация/валидация) не менялась
**Проверка себя:** тот же curl-набор, что использовался для 2.4-2.6 (фильтр, сортировка, пагинация, их комбинации, невалидные значения) — поведение идентично, это чистый рефакторинг формы запроса, не логики.

> По ходу задачи: (1) первая попытка объявить параметр в `MapGet` — `async (MovieService service, MovieQueryParameters) => ...`, без имени переменной; объявление параметра в C# — это всегда пара "тип + имя", а внутри тела при этом `MovieQueryParameters` использовался так, будто это переменная с готовым объектом, хотя это имя типа — отсюда и вопрос "где создаётся экземпляр"; прояснили, что экземпляр создаёт сам ASP.NET Core во время биндинга запроса — тем же способом, каким раньше он парсил `Status? status` по отдельности, только теперь сразу для всех полей объекта разом; (2) даже после того, как параметру дали имя, атрибут `[AsParameters]` был пропущен — без него сложный тип-параметр в Minimal API по умолчанию трактуется как тело запроса, а не query-string; на `GET`-маршруте это уронило приложение прямо при старте (`Body was inferred but the method does not allow inferred body parameters`) — сообщение framework само по себе прямым текстом объясняло, в чём проблема; (3) отдельно, в процессе финальной проверки, уточнение к более раннему выводу из 2.5: невалидный `sortBy` (`?sortBy=Banana`) действительно всегда отдавал `400`, но с сырым дампом `BadHttpRequestException` в теле ответа, не аккуратным сообщением — сравнение до/после через `git stash`/`git stash pop` (весь код сохранён в целости) подтвердило, что это поведение существовало уже в 2.5, не регресс сегодняшнего рефакторинга; не почищено, зафиксировано как известный шероховатый край — кандидат на отдельную будущую задачу про глобальный exception-handling/`ProblemDetails`.

### Задача 2.7: Поиск по названию `GET /movies` — ✅ ЗАКРЫТА
**Цель:** добавить текстовый поиск по `Title` тем же `IQueryable`-паттерном (`.Where()`), и столкнуться с разницей между "точное совпадение" (уже есть у `status`/`genre`) и "вхождение подстроки" — а также с регистрозависимостью SQL `LIKE` в Postgres и её обходом через `EF.Functions.ILike`.
**Шаги:**
- [x] `SearchPart` (`string?`) добавлен в `MovieQueryParameters` — седьмое поле того же объекта, без раздувания сигнатуры `MapGet`
- [x] `MovieService.GetMoviesAsync` — условный `.Where(m => EF.Functions.ILike(m.Title, $"%{...}%"))`, когда параметр передан и не пуст
- [x] Регистронезависимость — через `EF.Functions.ILike` (Npgsql-специфичный метод, транслируется в `ILIKE`), не через `.Contains()` (транслируется в регистрозависимый `LIKE`)
- [x] Пустой/несуществующий результат поиска — `200` с `[]`, тот же принцип, что закрепили в 2.6
**Проверка себя:** поиск по части названия в разных регистрах находит одно и то же; несуществующая подстрока — `200`, не `404`; поиск комбинируется с фильтром, сортировкой и пагинацией одним запросом.

> По ходу задачи — два бага в `MovieQueryParameters`, оба пойманы эмпирически и оба узнаваемы по прошлым задачам: (1) свойство `SearchPart` было инициализировано литералом `= string.Empty`, а не `= searchPart` (параметром primary-конструктора) — компилятор сам предупредил (`warning CS9113: Параметр "searchPart" не прочитан`); в результате поиск не работал вообще ни при каком значении параметра — `?searchPart=Лассо` возвращал все фильмы без фильтрации, потому что `SearchPart` внутри объекта всегда оставался пустой строкой; та же категория ошибки, что была с неиспользованным `maxRating` в 2.5; (2) `string searchPart` (без `?`) в конструкторе — то же самое дежавю, что `int pageSize` в 2.6: non-nullable параметр, биндящийся через `[AsParameters]`, ASP.NET Core считает обязательным, и `GET /movies` без единого параметра стал отдавать `400 "Required parameter string SearchPart was not provided"`, ломая все прошлые сценарии разом; поправлено на `string?`.

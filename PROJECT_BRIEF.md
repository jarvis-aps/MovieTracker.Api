## Цель

Не просто получить готовое приложение, а разобраться в современной backend/frontend разработке на практике: EF Core, ASP.NET Core, модульная архитектура, контейнеризация, распределённый деплой — и параллельно выработать рабочий процесс с ИИ-агентами, при котором понимание кода не теряется.

Приложение: трекер просмотренных фильмов. Стартует с одной таблицы (`Movies`: название + статус), дальше растёт по сложности данных, бэкенда, фронта и инфраструктуры — четырьмя отдельными, не обязательно синхронными осями.

## Стек

- **.NET 10** — не 9. .NET 8 и .NET 9 теряют поддержку Microsoft 10 ноября 2026, актуальный LTS — десятка, поддержка до ноября 2028.
- **EF Core** + PostgreSQL (пакет Npgsql.EntityFrameworkCore.PostgreSQL)
- **Mediator-паттерн** — только с этапа 3, когда появятся модули. MediatR ушёл на коммерческую лицензию в 2025-м (бесплатная Community-редакция для индивидуальных разработчиков и компаний с доходом до $5 млн — для пет-проекта не проблема), но раз цель этого проекта — понимание, а не готовое решение, разумная альтернатива — написать свой мини-mediator на 20-30 строк.
- **React + TypeScript** на фронте — но не с первого этапа. Этап 1 обходится без стейт-менеджера вообще.

## Философия проекта

1. **Сложность вводится по необходимости, а не заранее.** Модульный монолит, CQRS, слои — появляются, когда есть реальный повод (второй домен, вторая сущность, реальная бизнес-логика), а не потому что "так принято". Архитектура, добавленная без повода, — тот же нейро-слоп, только не от агента, а от преждевременного дизайна.
2. **Данные / бэкенд / фронт / инфраструктура — четыре независимые оси.** Не обязаны расти синхронно. Можно контейнеризировать рано, если хочется пощупать пораньше, или задержаться на локальном стенде, если фокус пока на бэке.
3. **Понимание — приоритет номер один.** Важнее скорости и важнее "правильной" архитектуры с первого раза.

## Режим работы агента: наставник, а не исполнитель

Это обязательное правило работы для любого агента (Claude Code, Claude в чате или другой), который работает по этому брифу — не рекомендация.

### Этап 1 — строгий режим

- Агент **не пишет реализацию** за пользователя.
- На каждую задачу агент выдаёт: **цель** (что это должно объяснить или натренировать), **чек-лист шагов**, **критерий готовности**. Формат — см. ниже.
- Пользователь реализует сам.
- Агент проверяет результат (код, вывод, поведение), указывает на конкретные проблемы и задаёт наводящие вопросы — не переписывает молча.
- Если пользователь застрял — агент может показать короткий (1-3 строки) фрагмент-подсказку, но обязан объяснить, почему именно так, а не просто вставить рабочий код.
- Задачи выдаются **по одной**, не все сразу.

### Этап 2+ — частичное послабление

Разрешено делегировать агенту:
- миграции EF Core
- DTO-мапинг
- повторяющийся CRUD-boilerplate **по уже установленному пользователем паттерну**

**Актуально с начала этапа 2:** пользователь явно попросил не пользоваться этим послаблением по умолчанию. Подробный режим этапа 1 (детальные шаги + объяснение "почему так, а не иначе" на каждом шаге) остаётся включён, пока пользователь лично не отменит явным сообщением — не сокращать формат задач автоматически при смене этапа.

Не разрешено делегировать никогда (в том числе на этапах 4-5):
- границы модулей и что уходит в событие / что в прямой вызов
- дизайн модели данных
- дизайн запросов и их сложность

Для делегированных кусков агент всё равно кратко объясняет, что сделал, если пользователь не знаком с деталью реализации.

- Пользователь может объяснить свой код своими словами, без агента.
- Минимум одна фича за этап сделана самостоятельно, без ИИ, за разумное время. Если тяжело — не двигаться дальше, закрепить текущий уровень.

### Задача 1.4: PATCH /movies/{id}/status — ✅ ЗАКРЫТА
**Цель:** первый write-эндпоинт
**Шаги:**
- [x] Minimal API endpoint `PATCH /movies/{id}/status`
- [x] Обновление через DbContext, SaveChanges
- [x] Обработка кейса "фильм не найден" (404)
- [x] Проверить через curl/Postman
**Проверка себя:** статус меняется в БД, повторный GET показывает изменение.

> По ходу задачи: (1) новый статус передаётся через query-параметр (`?status=Watched`) — параметр `Status status` в хендлере ASP.NET Core сам биндит из query string по конвенции (любой тип с `TryParse`, включая enum, без атрибута `[FromQuery]`); отсутствие параметра само по себе даёт 400 с понятным сообщением; (2) была путаница между "найти фильм" (внутренний шаг сервера через `FirstOrDefaultAsync`, нужен для change tracking) и "узнать статус" (это уже закрыто в `GET /movies`) — важно: PATCH это один запрос с двумя данными сразу (`id` из пути + новый статус из query), не два отдельных эндпоинта; (3) сквозная проверка — успешный патч (200, реально меняет `Status` в Postgres), 404 на несуществующий id, 400 без обязательного параметра. Мелкий незакрытый нюанс: `SaveChanges()` синхронный внутри async-хендлера (стилистически лучше `SaveChangesAsync()`, не блокирует задачу).

**Реальные баги, найденные и исправленные пользователем самостоятельно по ходу ревью (не агентом):**
1. Первая версия читала `title`/`status` из query-string, а не из тела — не соответствовало критерию. Поправлено на DTO (`NewMovie newMovie` параметром), подтверждено эмпирически (тело реально стало читаться, а не игнорироваться).
2. Побочно всплыла разница между биндингом enum из route/query (`TryParse`, принимает имя типа `"Watched"`) и из JSON-тела (`System.Text.Json`, по умолчанию — число, не имя) — не баг, а особенность двух разных механизмов ASP.NET Core, зафиксирована для памяти.
3. Конструктор `Movie(string title, Status status)` не присваивал `Status = status` — все фильмы через `POST` создавались с дефолтным `Status.Watched` независимо от запроса. Найдено эмпирически (в БД оказывалось не то значение, что просили), исправлено.
4. `Results.Created($"/movies/{movie.Title}", ...)` — использование `Title` вместо `Id` в URL реально **уронило приложение с 500** (кириллица в HTTP-заголовке `Location` — недопустимый символ вне ASCII). Поправлено на `movie.Id` — заодно разобрали, почему ресурсы в REST адресуют по `Id`, а не по произвольному тексту.
5. В ответе возвращался `newMovie` (входной DTO, эхо запроса, без `Id`) вместо `movie` (реально сохранённая сущность) — маскировало баг №3 в самом ответе API. Поправлено на возврат `movie`.

Все пять пунктов пользователь нашёл и исправил сам после того, как агент показывал результат эмпирической проверки (curl + прямой запрос в БД) и объяснял, *почему* именно так — не давая готового кода.

## Этап 2 — детальный план

### Задача 2.1: DTO для ответов API — ✅ ЗАКРЫТА
**Цель:** отделить контракт API (что видит клиент) от EF-сущности (модель БД), пока это не составляет труда — сейчас у `Movie` три поля, до роста домена (`Year`/`Rating`/`Notes`/`Genre`) сделать это проще, чем после.
**Шаги:**
- [x] `MovieDto` — `record` (`public record MovieDto(int Id, string Title, Status Status);`), не класс — DTO не меняется после создания, `record` даёт неизменяемость и позиционный конструктор "из коробки"
- [x] `GET /movies` возвращает `List<MovieDto>`, маппинг вручную через `Select`
- [x] `POST /movies` в `Results.Created` возвращает `MovieDto` (собран после `SaveChangesAsync`, когда `Id` уже реальный)
- [x] `PATCH /movies/{id}/status` тоже переведён на `MovieDto` целиком (не только `Status`) — осознанное решение: клиент сразу видит весь актуальный фильм после апдейта, без лишнего `GET`; полезно уже сейчас, не только "на будущее"
**Проверка себя:** `DbContext`/`SaveChanges` работают исключительно с `Movie`, `MovieDto` не участвует в персистентности — только в самом последнем шаге перед `return`. Сквозная проверка через curl — все три эндпоинта отдают `MovieDto`, поведение (200/201/404) не сломано.

> По ходу задачи: (1) `NewMovie` (входной DTO для `POST`) и `MovieDto` (выходной) — сознательно разные типы, не слиты в один, хотя сейчас совпадают по полям: вход не должен допускать `Id` (генерируется базой), выход — должен его показывать; (2) была путаница про роль `DbContext` в этом паттерне — прояснили, что `DbSet<Movie> Movies` не трогается вообще, `MovieDto` не имеет отношения к персистентности, существует только на границе API.

### Задача 2.2: Service-слой — ✅ ЗАКРЫТА
**Цель:** вынести логику работы с БД из хендлеров `Program.cs` в `MovieService` — `Program.cs` остаётся тонким слоем маршрутизации, не местом, где живёт логика.
**Шаги:**
- [x] `Services/MovieService.cs` — методы `GetMoviesAsync()`, `UpdateStatusAsync(id, status)`, `CreateMovieAsync(newMovie)`, все без единого упоминания HTTP/`WebApplication`/`Results.*`, только `MovieTrackerDbContext` через конструктор
- [x] "Не найдено"/"дубликат" сигнализируется через `null`-возврат сервиса — хендлер сам решает, во что это превратить (`Results.NotFound()`/`Results.BadRequest()`) — HTTP-семантика осталась снаружи сервиса
- [x] `builder.Services.AddScoped<MovieService>()` — регистрация в DI, **до** `builder.Build()`
- [x] Хендлеры в `Program.cs` укорочены до 1-3 строк каждый
**Проверка себя:** поведение всех трёх эндпоинтов (200/201/404, содержимое ответов) не изменилось — чистый рефакторинг, подтверждено сквозным прогоном через curl.

> По ходу задачи — две ошибки первой попытки, обе показательные: (1) первая версия `MovieService` принимала `WebApplication` в конструктор и сама вызывала `MapGet`/`MapPatch`/`MapPost` внутри своих методов — инвертировало границу ответственности (сервис не должен знать про HTTP/роутинг вообще), к тому же эти методы никогда не вызывались — эндпоинты фактически не регистрировались; переписано на чистые методы, возвращающие C#-объекты; (2) `builder.Services.AddScoped<MovieService>()` изначально был добавлен **после** `builder.Build()` — `IServiceCollection` "запекается" и становится read-only в момент `Build()`, поймано рантайм-исключением при старте, перенесено до `Build()`.

### Задача 2.3: Рост домена — новые поля Movie — ✅ ЗАКРЫТА
**Цель:** расширить модель данных за пределы `Title`+`Status` и провести это изменение через реальный EF Core migration workflow на непустой таблице (в отличие от 1.2, где таблица создавалась с нуля).
**Шаги:**
- [x] `Movie` расширен полями `Year` (`int`), `Rating` (`float`), `Genres` (`List<Genre>`, новый `enum Genre` — не FK-таблица; M:N-таблица `Genres` по дорожной карте это уже этап 3, здесь сознательно взят более простой вариант) — `Notes` отложен
- [x] Миграция `NewFields` (+ `updateNewFields` вторым проходом, см. ниже) применена, колонки на месте (`Year integer`, `Rating real`, `Genres integer[]`)
- [x] `MovieDto`, `NewMovie`, `MovieService` (все три метода) обновлены под новые поля
- [x] Новый эндпоинт `PATCH /movies/{id}/rating`, отдельно от `/status`
- [x] Валидация диапазона `rating` (0-10) — через кастомное `InvalidRatingException` (`Exceptions/InvalidRatingException.cs`), пойманное в хендлере и превращённое в `Results.BadRequest(exception.Message)`
- [x] Сквозная проверка через curl — `GET`, `POST` (`201` + `Location` + реальные поля), `PATCH /status`, `PATCH /rating` (валидный `200`, вне диапазона `400` с чистым сообщением, не стек-трейс)
**Проверка себя:** таблица `Movies` содержит новые колонки с ожидаемыми типами (подтверждено `psql`), все эндпоинты отдают консистентный `MovieDto`, `rating` вне диапазона даёт `400`, не `500`.

> По ходу задачи: (1) `Rating` был сначала объявлен `decimal`, затем осознанно перепланирован на `float` уже после того, как первая миграция (`NewFields`) была сгенерирована и применена — модель и уже применённая схема разошлись (`dotnet ef migrations has-pending-model-changes` подтвердил расхождение), понадобилась вторая миграция (`updateNewFields`), догоняющая тип колонки (`numeric` → `real`); (2) непустая колонка `NOT NULL` на непустой таблице потребовала `defaultValue` в миграции — старые сидинг-записи получили `Year=0`/`Rating=0`/`Genres={}` вместо честного `NULL`, который был бы возможен при `int?`; обсуждали, что `NULL` в таких случаях честнее фиктивного нуля — не переделано, зафиксировано как понятый компромисс; (3) сидинг-код (`if (!db.Movies.Any())`) не подхватил новые поля для трёх старых записей, пока их не удалили руками и не перезапустили приложение — сидинг выполняется только на пустой таблице, не при каждом старте; (4) первая попытка `POST /movies` с `"status":"NotWatched"` (строкой) упала — `System.Text.Json` по умолчанию биндит enum из JSON-тела как число, не как имя (то же самое правило, что было зафиксировано в закреплении этапа 1, только теперь применительно и к элементам `List<Genre>`); (5) первая попытка обработки `InvalidRatingException` в хендлере ловила исключение, логировала и делала `throw;` — то есть пробрасывала его дальше необработанным, клиент всё равно получал бы `500`; поправлено на `Results.BadRequest(exception.Message)` в `catch`-блоке.

> Отдельно, уже после закрытия 2.3, но до начала 2.4: перенос логирования невалидного рейтинга из хендлера в `MovieService` (решение — логировать ближе к месту нарушения бизнес-правила, а не только на HTTP-границе) дважды ломался по пути — сначала пропал `throw` внутри `if`-валидации (лог писался, но метод продолжал сохранять невалидный рейтинг и возвращал `200` вместо `400`), потом при повторной правке пропал весь `try/catch` вокруг вызова сервиса в `Program.cs` (исключение стало долетать необработанным до клиента как `500`). Оба раза баг находился не чтением кода, а тем же самым способом, что и раньше — прогоном через curl с заведомо невалидным значением и проверкой реального кода ответа.

### Задача 2.4: Фильтрация `GET /movies` — ✅ ЗАКРЫТА
**Цель:** спроектировать опциональные query-параметры фильтра и разобраться с `IQueryable` — условный `.Where(...)`, транслируемый в SQL и выполняемый в Postgres, а не в памяти после `ToListAsync()`.
**Шаги:**
- [x] `GET /movies` принимает необязательные `status` (`Status?`) и `genre` (`Genre?`)
- [x] `MovieService.GetMoviesAsync(Status? status, Genre? genre)` строит `IQueryable<Movie>`, добавляя `.Where(...)` только для переданных параметров — переприсваивание одной и той же переменной `query`, а не отдельные ветки на разные списки
- [x] Без фильтров — полный список, как раньше
- [x] Фильтр по `genre` — проверка вхождения в `List<Genre>` (`.Contains(...)`), не равенство
- [x] Маппинг в `MovieDto` — после `ToListAsync()`, на уже отфильтрованном результате
**Проверка себя:** curl с `?status=`, `?genre=`, обоими сразу и без параметров — в каждом случае верное подмножество; исходно пустая база не мешает удостовериться, что фильтрация уходит в SQL, а не в C# после загрузки всех строк.

> По ходу задачи — три показательные ошибки первой попытки: (1) вместо одного эндпоинта с опциональными параметрами были заведены три отдельных `MapGet("/movies", ...)` — один без параметров, по одному на `status` и на `genre`; ASP.NET Core матчит маршрут по пути и HTTP-методу до какого-либо биндинга параметров, поэтому три идентичных по шаблону маршрута дают `AmbiguousMatchException` на любой запрос (компилятор предупреждает об этом сам, `warning ASP0022`), и вдобавок с раздельными эндпоинтами нет способа применить оба фильтра одним запросом — при росте числа независимых фильтров (следом идут сортировка/поиск/пагинация) число нужных комбинаций-эндпоинтов растёт как 2ⁿ; поправлено на один эндпоинт с `Status?`/`Genre?`; (2) первая версия фильтрации грузила `_context.Movies.ToListAsync()` **до** `.Where(...)` и фильтровала уже материализованный `List<Movie>`/`List<MovieDto>` в C# — на 3-5 тестовых записях разницы не видно, но это означает выкачивание всей таблицы по сети при каждом запросе вместо `WHERE` в самом SQL; поправлено на построение `IQueryable` и условный `.Where()` до `ToListAsync()`; (3) при живой проверке `?genre=Sport` вернул пустой список, хотя один из сидинг-фильмов явно содержал `Genre.Sport` — причина оказалась не в фильтре, а в данных: `Genre` хранится в Postgres как голое число (позиция в enum), а более ранняя правка того же дня (удаление дублей `Romance`/`Romantic`, `SciFi`/`ScienceFiction` из середины списка) сдвинула числовые коды всех элементов после них, и уже сохранённая в базе запись осталась с устаревшим числом, не соответствующим новому `Genre.Sport`; исправлено фиксацией явных числовых значений у всех членов `Genre` (`Action = 0, ...`) и пересидингом таблицы — зафиксировано на будущее: правка enum, уже используемого в БД, без явных значений тихо портит существующие данные.

## Как пользоваться этим документом

Файл кладётся в корень репозитория. Задачи выдаются по одной, не все сразу — прогресс идёт через цикл "задача → реализация → проверка → следующая задача". Детальные планы для этапов 2-5 составляются по этому же принципу, когда до них доходит очередь: заранее расписывать их означает планировать то, что ещё может измениться по ходу этапа 1.

После каждой закрытой задачи — обновляй раздел "Текущий статус" в начале файла (что сделано, что уточнилось по факту, какая задача следующая) и отмечай чек-листы галочками. Не оставляй его как есть: это единственное место, по которому можно понять, где именно остановилась работа, не пересказывая всю историю чата.

# Памятка: термины и технологии .NET backend

Обновлено: 2026-10-05. Справочник терминов из `Roadmap.excalidraw` и двух видео автора; связан с разделом «Карта тем» в `PROJECT_BRIEF.md`.

## C#: база языка

**Класс** — это шаблон, описывающий данные (поля, свойства) и поведение (методы) объекта; нужен для моделирования предметной области: `Movie`, `User` в проекте — это классы.

**ООП (инкапсуляция, наследование, полиморфизм, абстракция)** — это подход, где программа строится из взаимодействующих объектов: инкапсуляция прячет внутреннее состояние, наследование переиспользует базовый тип, полиморфизм позволяет работать с разными типами через общий интерфейс, абстракция выделяет главное и скрывает детали; нужен, чтобы код было проще расширять и менять, не ломая остальное.

**Интерфейс** — это контракт: набор членов без реализации; нужен, чтобы зависеть от абстракции, а не от конкретного класса (на этом держатся внедрение зависимостей и подмена в тестах).

**Коллекции (List, Dictionary, HashSet, Queue)** — это готовые структуры для хранения набора элементов; нужны для выбора правильной структуры под задачу: поиск по ключу в `Dictionary` почти мгновенный, в `List` — перебором.

**Значимые и ссылочные типы** — значимые (`int`, `struct`, `enum`) хранят само значение и копируются при присваивании, ссылочные (`class`, `string`, массивы) хранят ссылку на объект в куче; нужно понимать, чтобы предсказуемо передавать данные в методы, сравнивать объекты и не создавать лишнюю нагрузку на сборщик мусора.

**Строки (string, StringBuilder)** — `string` неизменяема: любая «правка» создаёт новую строку, `StringBuilder` копит изменения в буфере; нужны, чтобы не плодить мусор при сборке больших текстов в циклах.

**Работа с файлами (File, Stream, Path)** — это API для чтения и записи файлов и потоков байтов; нужен для импорта и экспорта, загрузки файлов, чтения конфигов; потоки позволяют обрабатывать большие файлы, не загружая их целиком в память.

**Делегаты и события (delegate, Func, Action, event)** — делегат это тип, хранящий ссылку на метод, `Func` и `Action` — готовые обобщённые варианты, событие — механизм подписки на уведомления; нужны для передачи поведения в метод (на этом построены LINQ и middleware) и для реакции на происшествия.

**Исключения (try/catch/finally, throw)** — это механизм сообщения об ошибках во время выполнения; нужен, чтобы обрабатывать сбои контролируемо: в веб-API ошибка превращается в корректный HTTP-ответ, а не роняет приложение.

**Generics (обобщения)** — это типы и методы с параметром типа, например `List<T>`; нужны для переиспользуемого кода без приведения типов и с проверкой на этапе компиляции.

**record** — это тип с равенством по значению, неизменяемостью по умолчанию и выражением `with` для копии с правкой; нужен для DTO, команд и событий, где важны данные, а не поведение.

**LINQ** — это язык запросов к коллекциям (`Where`, `Select`, `GroupBy`, `OrderBy`); нужен для фильтрации и преобразования данных; EF Core транслирует такие запросы в SQL.

**Многопоточность (Thread, Task, lock)** — это одновременное выполнение нескольких задач: `Thread` — поток ОС, `Task` — абстракция над задачей, `lock` — защита общих данных от одновременной правки; нужна, чтобы использовать все ядра, а в вебе сервер и так обрабатывает запросы параллельно, поэтому общее изменяемое состояние становится источником гонок.

**async/await** — это синтаксис асинхронного кода: пока идёт ожидание ввода-вывода (БД, сеть, диск), поток не простаивает, а обслуживает другие запросы; нужен, чтобы сервер выдерживал много одновременных запросов малым числом потоков.

## Базовые инструменты

**Git** — это система контроля версий: хранит историю изменений кода и позволяет работать в ветках; нужна, чтобы откатываться, сравнивать версии и безопасно пробовать идеи, не ломая рабочий код.

**GitHub** — это сервис хостинга Git-репозиториев с Pull Request, ревью и CI; нужен для совместной работы, ревью кода и как портфолио.

**Ветки и Pull Request** — ветка это независимая линия изменений, Pull Request — предложение влить ветку в основную с обсуждением; нужны для изолированной работы над задачей и ревью до слияния.

**NuGet** — это менеджер пакетов .NET: библиотеки подключаются командой или через IDE; нужен, чтобы не писать с нуля то, что уже есть (EF Core, Serilog, xUnit — все ставятся через него).

**.NET SDK и Runtime** — SDK включает компилятор и утилиты для сборки, Runtime только запускает готовое приложение; нужны: SDK на машине разработчика, Runtime на сервере.

**dotnet CLI** — это консольная утилита (`dotnet build`, `run`, `test`, `ef`); нужна для сборки, запуска, тестов и миграций без IDE, в том числе в CI.

**IDE (Rider, Visual Studio)** — это среда разработки с отладчиком, рефакторингами и подсказками; нужна для ускорения написания кода и поиска ошибок.

**HTTP-клиент (Postman, Insomnia, файлы `.http`)** — это инструмент для отправки запросов к API вручную; нужен, чтобы проверять эндпоинты, не дожидаясь готового фронтенда.

**SQL-клиент (DBeaver, pgAdmin, psql)** — это инструмент для просмотра и запросов к базе напрямую; нужен, чтобы убедиться, что данные и миграции выглядят так, как задумано.

## ASP.NET Core Web API

**HTTP** — это протокол «запрос — ответ», по которому клиент (браузер, приложение) общается с сервером; нужен как основа любого веб-API. Запрос состоит из метода, URL, заголовков и тела, ответ — из статус-кода, заголовков и тела.

**HTTP-методы и статус-коды** — методы (`GET` читает, `POST` создаёт, `PUT` и `PATCH` меняют, `DELETE` удаляет) говорят, что сделать; коды (`200` ок, `201` создано, `400` ошибка клиента, `401` не авторизован, `403` нет прав, `404` не найдено, `500` ошибка сервера) говорят, чем закончилось; нужны, чтобы клиент однозначно понимал результат без разбора текста.

**REST API** — это стиль проектирования API, где данные представлены ресурсами с адресами (`/movies/5`), а действия задаются HTTP-методами; нужен, чтобы API был предсказуемым и понятным любому клиенту.

**ASP.NET Core** — это веб-фреймворк .NET для создания HTTP-приложений и API; нужен как основа бэкенда: принимает запрос, прогоняет через конвейер и возвращает ответ.

**Kestrel** — это встроенный кроссплатформенный веб-сервер ASP.NET Core; нужен, чтобы приложение само принимало HTTP-запросы, обычно за обратным прокси вроде NGINX.

**Minimal API** — это стиль, где эндпоинты описываются короткими вызовами `app.MapGet(...)` без классов-контроллеров; нужен для компактных API с минимумом церемоний (так сделан MovieTracker).

**Controllers** — это классы с методами-действиями, помеченными атрибутами (`[HttpGet]`, `[Route]`); нужны для группировки эндпоинтов и использования готовых фильтров и атрибутов в крупных API; альтернатива Minimal API.

**Routing (маршрутизация)** — это сопоставление URL и HTTP-метода с обработчиком; нужна, чтобы запрос `GET /movies/5` попал в нужный код, а `5` пришло параметром.

**Middleware** — это звено конвейера обработки запроса: каждое может выполнить код до и после следующего или оборвать цепочку; нужны для сквозных задач — логирования, авторизации, обработки ошибок, CORS, сжатия.

**Dependency Injection (DI)** — это приём, при котором класс не создаёт свои зависимости сам, а получает их снаружи (обычно через конструктор), а контейнер ASP.NET Core собирает объекты; нужен, чтобы слабо связывать части кода и подменять реализации, например в тестах.

**Время жизни сервисов (Singleton, Scoped, Transient)** — задаёт, как долго живёт объект: один на всё приложение, один на запрос или новый при каждом запросе; нужно знать, чтобы не получить утечки состояния между запросами (`DbContext` — Scoped).

**Конфигурация (appsettings.json, Options, переменные окружения)** — это способ вынести настройки (строки подключения, ключи, лимиты) из кода; нужна, чтобы одно приложение работало в разных окружениях без пересборки, а секреты не лежали в репозитории.

**Swagger / OpenAPI** — OpenAPI это стандарт машинного описания REST API, Swagger — набор инструментов вокруг него, включая страницу для проб запросов; нужны как живая документация и для генерации клиентов.

**DTO (Data Transfer Object)** — это отдельный объект только для передачи данных через границу API; нужен, чтобы не отдавать наружу внутренние модели БД, не светить лишние поля и менять БД, не ломая контракт API.

**Маппинг (Mapster, AutoMapper)** — это преобразование одного объекта в другой, например сущности в DTO; нужен, чтобы не писать копирование полей вручную; в простых проектах часто достаточно ручного маппинга.

## База данных

**Реляционная БД и SQL** — реляционная БД хранит данные в связанных таблицах, SQL — язык запросов к ней; нужны для надёжного хранения структурированных данных, где важны связи и целостность.

**PostgreSQL** — это свободная реляционная СУБД с богатыми типами (JSON, массивы), полнотекстовым поиском и расширениями; нужна как основное хранилище данных проекта.

**ORM** — это слой, который отображает таблицы БД на классы и сам формирует SQL; нужен, чтобы работать с данными на C#, а не писать SQL руками для каждой операции.

**EF Core (Entity Framework Core)** — это основной ORM для .NET: умеет отслеживать изменения, строить SQL из LINQ и применять миграции; нужен для типового доступа к данным (CRUD, связи, миграции).

**Миграции** — это версионированные скрипты изменения схемы БД, генерируемые EF Core из изменений модели; нужны, чтобы схема менялась воспроизводимо и одинаково на всех окружениях.

**Связи (1:1, 1:N, M:N, внешний ключ)** — внешний ключ ссылается на строку другой таблицы, а виды связей описывают, сколько записей с каждой стороны; нужны для моделирования данных без дублирования (фильм — жанры — многие ко многим).

**Dapper** — это микро-ORM: выполняет ваш SQL и маппит результат на объекты; нужен для быстрых сложных запросов и отчётов, где EF Core избыточен или медленнее.

**ACID** — это четыре свойства надёжной транзакции: атомарность (всё или ничего), согласованность (данные остаются корректными), изолированность (параллельные операции не мешают друг другу), долговечность (зафиксированное не пропадёт); нужны, чтобы данные не портились при сбоях и конкуренции.

**Транзакции** — это группа операций, выполняемая как одно целое: либо применяются все, либо ни одна; нужны там, где несколько изменений должны быть согласованы (например, списать и начислить).

**Уровни изоляции транзакций** — это настройка того, что одна транзакция видит из незавершённых изменений другой (Read Committed, Repeatable Read, Serializable); нужна для баланса между корректностью данных и скоростью.

**Индексы** — это дополнительные структуры (чаще B-tree), которые ускоряют поиск и сортировку по колонке за счёт места и скорости записи; нужны, чтобы запросы не сканировали всю таблицу.

**Проблема N+1** — это ситуация, когда на один запрос списка приходится ещё N запросов за связанными данными; нужно знать, чтобы вовремя использовать `Include` или проекции и не убить производительность.

**Нормализация** — это приведение схемы к виду без дублирования данных (нормальные формы); нужна для целостности и простоты изменения данных, иногда осознанно нарушается ради скорости чтения.

**Change Tracker и `AsNoTracking`** — Change Tracker следит за изменениями загруженных сущностей, чтобы `SaveChanges` записал только разницу, а `AsNoTracking` отключает слежение; нужен `AsNoTracking` для запросов только на чтение — быстрее и дешевле по памяти.

## Чистая архитектура

**Clean Architecture** — это способ организации кода слоями вокруг бизнес-логики, при котором внутренние слои ничего не знают о внешних (БД, веб, фреймворки); нужна, чтобы бизнес-правила не зависели от инфраструктуры и их можно было тестировать и менять отдельно.

**Слои (Domain, Application, Infrastructure, Presentation)** — Domain хранит сущности и правила, Application — сценарии использования, Infrastructure — БД и внешние сервисы, Presentation — API; нужны, чтобы у каждой части кода была одна зона ответственности.

**Правило зависимостей** — это принцип: зависимости в коде направлены только внутрь, к Domain, а внешние слои реализуют интерфейсы, объявленные внутри; нужно, чтобы замена БД или фреймворка не затрагивала бизнес-логику.

**Разделение ответственности (Separation of Concerns)** — это принцип, по которому каждый модуль решает одну задачу; нужен, чтобы код проще читался, менялся и тестировался.

**Монолит и модульный монолит** — монолит это одно развёртываемое приложение, модульный монолит делит его на изолированные модули с чёткими границами; нужны как простая отправная точка, из которой при реальной необходимости можно выделить микросервисы.

**Паттерн Repository** — это абстракция над доступом к данным, скрывающая запросы за интерфейсом; нужен, чтобы подменять хранилище в тестах, но поверх EF Core он часто дублирует `DbContext`, поэтому в проекте это спорный пункт бэклога.

**Unit of Work** — это объект, который собирает изменения и применяет их одной транзакцией; в EF Core эту роль уже играет `DbContext` (`SaveChanges`); нужен для атомарной записи нескольких изменений.

## Проектирование классов и домена

**Сущность (Entity)** — это объект предметной области со своей идентичностью (`Id`), который живёт во времени и меняется; нужна, чтобы отличать «тот самый фильм» от другого с такими же полями.

**Анемичная модель** — это подход, где классы хранят только данные (свойства), а вся логика лежит в сервисах; нужна как простой старт для небольших CRUD-приложений, но при росте правил логика размазывается по сервисам.

**Богатая модель (Rich Domain Model)** — это подход, где сущность сама хранит данные и правила их изменения (методы вроде `Rate(...)`, `ChangeStatus(...)`); нужна, чтобы нельзя было перевести объект в некорректное состояние и чтобы бизнес-правила были в одном месте.

**Инварианты** — это условия, которые всегда должны выполняться для объекта (рейтинг от 1 до 10, название не пустое); нужны, чтобы объект в памяти и в БД не мог оказаться «сломанным»; их защищает конструктор или методы богатой модели.

**Result pattern** — это возврат из метода объекта-результата («успех» или «ошибка с описанием») вместо выброса исключения; нужен, чтобы ожидаемые бизнес-ошибки (не найдено, нарушено правило) не гонять через исключения — это явнее в коде и дешевле по производительности.

## Валидация

**Валидация** — это проверка входных данных до того, как они попадут в логику и БД; нужна, чтобы отсеять мусор и злоупотребления на границе системы и вернуть клиенту понятную ошибку `400`.

**DataAnnotations** — это встроенные атрибуты (`[Required]`, `[Range]`, `[MaxLength]`) прямо на свойствах модели; нужны для простых проверок без дополнительных библиотек.

**FluentValidation** — это библиотека, где правила описываются отдельным классом-валидатором в виде цепочки вызовов (`RuleFor(x => x.Title).NotEmpty().MaximumLength(200)`); нужна для сложных и условных правил, которые неудобно держать в атрибутах, и для разделения правил и моделей.

**Уровни валидации** — это разделение проверок: формат данных (пустая строка, длина) проверяется на входе API, бизнес-правила (нельзя оценить непросмотренный фильм) — в домене, а целостность — ограничениями БД; нужно, чтобы каждая проверка жила на своём уровне и не дублировалась.

**ProblemDetails (RFC 7807 / 9457)** — это стандартный JSON-формат ответа об ошибке (`type`, `title`, `status`, `detail`); нужен, чтобы все ошибки API выглядели одинаково и клиент мог обрабатывать их единообразно.

## Логирование

**Логирование** — это запись событий работы приложения (запрос принят, ошибка, медленный запрос); нужно, чтобы разбираться, что происходило в проде, когда отладчика рядом нет.

**ILogger и уровни логов** — `ILogger<T>` это стандартный интерфейс логирования в .NET, а уровни (`Trace`, `Debug`, `Information`, `Warning`, `Error`, `Critical`) показывают важность записи; нужны, чтобы в проде включать только нужное и не тонуть в шуме.

**Структурное логирование** — это запись логов не как строк, а как событий с именованными полями (`{MovieId}`, `{UserId}`); нужно, чтобы потом искать и фильтровать логи по значениям полей, а не парсить текст.

**Serilog** — это популярная библиотека структурного логирования для .NET, которая пишет логи в разные приёмники; нужна как более гибкая замена стандартному выводу: форматы, обогащение данными, настройка через конфиг.

**Sink (приёмник)** — это место, куда Serilog отправляет логи (консоль, файл, Seq, Elasticsearch); нужен, чтобы менять назначение логов, не трогая код, который их пишет.

**Seq** — это сервер для сбора и просмотра структурных логов с поиском и фильтрами; нужен как лёгкий способ удобно читать логи на локальной машине и на небольших стендах.

**Elastic Stack (ELK: Elasticsearch, Logstash, Kibana)** — это набор для централизованного хранения, поиска и визуализации логов: Elasticsearch хранит и ищет, Logstash собирает и преобразует, Kibana показывает; нужен для больших систем, где логи многих сервисов надо искать в одном месте.

**Correlation ID** — это уникальный идентификатор запроса, который попадает во все его логи и передаётся между сервисами; нужен, чтобы собрать воедино весь путь одного запроса.

## CQRS

**CQRS (Command Query Responsibility Segregation)** — это разделение операций на команды (меняют состояние) и запросы (только читают) с отдельными моделями и путями выполнения; нужен, чтобы независимо оптимизировать чтение и запись и не смешивать сложную бизнес-логику с выборками.

**Command и Query** — команда это запрос на изменение (`CreateMovie`, `RateMovie`), который ничего не возвращает или возвращает только результат операции, запрос это чтение (`GetMovies`), которое ничего не меняет; нужны как явные объекты, по которым понятно, что умеет приложение.

**Handler (обработчик)** — это класс, который выполняет ровно одну команду или один запрос; нужен, чтобы каждая операция жила в отдельном небольшом классе, а не в разросшемся сервисе.

**Read model** — это отдельная модель данных, оптимизированная только под чтение (проекции, денормализованные таблицы, Dapper-запросы); нужна, чтобы выборки были быстрыми и не тянули за собой сущности домена.

**MediatR** — это библиотека-посредник: отправляешь команду или запрос, а она находит нужный обработчик, и позволяет добавлять сквозное поведение (логирование, валидацию) через pipeline; нужна как популярный способ реализовать CQRS. Условия лицензии в новых версиях стоит проверить перед использованием.

**Pipeline behavior** — это обёртка вокруг обработчика, которая выполняется до и после него; нужна для сквозных задач — валидация, логирование, транзакция — без дублирования кода в каждом обработчике.

## Кэширование

**Кэш** — это быстрое временное хранилище результатов дорогих операций (запрос в БД, вызов внешнего API); нужен, чтобы отдавать повторяющиеся данные быстро и снижать нагрузку на БД.

**Cache hit / miss и TTL** — hit это когда нужное значение нашлось в кэше, miss когда нет и пришлось идти за данными, TTL это время жизни записи до автоматического удаления; нужны, чтобы оценивать эффективность кэша и не отдавать слишком старые данные.

**In-memory cache (`IMemoryCache`)** — это кэш в памяти одного процесса приложения; нужен для простых случаев, но у каждого экземпляра приложения он свой, поэтому при нескольких экземплярах данные расходятся.

**Distributed cache (`IDistributedCache`)** — это общий кэш, вынесенный в отдельный сервис, который видят все экземпляры приложения; нужен, чтобы при горизонтальном масштабировании все работали с одними и теми же закэшированными данными.

**Redis** — это очень быстрая база «ключ — значение» в памяти с TTL, структурами данных и pub/sub; нужна как основной распределённый кэш, а также для сессий, счётчиков, лимитов запросов и очередей.

**Cache-aside** — это самый частый шаблон: приложение сначала смотрит в кэш, при промахе читает из БД и кладёт результат в кэш; нужен как простой способ добавить кэш, не меняя основное хранилище.

**Инвалидация кэша** — это удаление или обновление записей, когда исходные данные изменились; нужна, чтобы пользователь не видел устаревшее — это самая сложная часть кэширования.

**HybridCache и Output caching** — HybridCache (в .NET 9+) сочетает кэш в памяти и распределённый с защитой от одновременных одинаковых запросов, Output caching кэширует готовые HTTP-ответы целиком; нужны, чтобы получить кэширование «из коробки» без самописной обвязки.

## Docker и Kubernetes

**Контейнер** — это изолированный процесс со своим набором файлов и зависимостей, который запускается одинаково на любой машине; нужен, чтобы убрать «у меня работает, а на сервере нет» и быстро поднимать окружение.

**Docker** — это платформа для сборки образов и запуска контейнеров; нужна, чтобы упаковать приложение со всем окружением и запускать БД, кэш и брокеры одной командой (в проекте PostgreSQL уже работает в Docker).

**Образ (image) и Dockerfile** — образ это неизменяемый шаблон, из которого запускаются контейнеры, Dockerfile это текстовая инструкция его сборки; нужны, чтобы воспроизводимо собирать и доставлять приложение.

**Multi-stage build** — это сборка образа в несколько этапов: тяжёлый SDK собирает код, в итоговый образ попадает только рантайм и результат; нужен, чтобы образы были маленькими и безопаснее.

**Docker Compose** — это описание нескольких контейнеров (API, Postgres, Redis) в одном `docker-compose.yml`; нужен, чтобы поднимать всё окружение проекта одной командой.

**Volume** — это хранилище вне контейнера, которое переживает его пересоздание; нужен, чтобы данные БД не пропадали при перезапуске контейнера.

**Registry (Docker Hub, GHCR)** — это хранилище образов, откуда их скачивают на серверы; нужен для доставки собранных образов в среды.

**CI/CD (GitHub Actions)** — это автоматическая сборка, прогон тестов и выкладка при каждом изменении кода; нужны, чтобы ошибки находились сразу, а релиз не зависел от ручных действий.

**Kubernetes** — это система оркестрации: запускает множество контейнеров на кластере, перезапускает упавшие, масштабирует и раскатывает обновления без простоя; нужен, когда сервисов и нагрузки много. Для учебного проекта он в беклоге: достаточно понимать концепции.

**Объекты Kubernetes (Pod, Deployment, Service, Ingress, ConfigMap, Secret)** — Pod это минимальная единица запуска, Deployment управляет набором копий, Service даёт им стабильный адрес, Ingress пускает трафик снаружи, ConfigMap и Secret хранят настройки и секреты; нужны, чтобы описывать приложение в кластере декларативно.

## Аутентификация и авторизация

**Аутентификация и авторизация** — аутентификация отвечает на вопрос «кто ты» (логин, пароль, токен), авторизация на вопрос «что тебе можно»; нужны, чтобы данные видели и меняли только те, кому положено (в проекте — у каждого пользователя свои оценки и заметки).

**Хеширование паролей (PBKDF2, bcrypt, Argon2)** — это необратимое преобразование пароля с солью и замедлением; нужно, чтобы при утечке базы пароли нельзя было прочитать.

**JWT (JSON Web Token)** — это подписанный токен с данными о пользователе (claims), который клиент присылает в заголовке `Authorization`; нужен, чтобы сервер проверял личность без хранения сессии, что удобно для масштабирования.

**Access и Refresh token** — access-токен живёт коротко и ходит с каждым запросом, refresh-токен живёт долго и нужен только для получения нового access; нужны, чтобы украденный access быстро терял силу, а пользователю не приходилось постоянно логиниться.

**Claims** — это утверждения о пользователе внутри токена (id, роль, email); нужны, чтобы сервер знал, кто делает запрос, и принимал решения о доступе.

**RBAC (Role-Based Access Control)** — это модель доступа по ролям: права выдаются роли (`Admin`, `User`), а роль назначается пользователю; нужна для простого и понятного разграничения прав.

**ABAC (Attribute-Based Access Control)** — это модель доступа по атрибутам пользователя, ресурса и контекста («редактировать можно только свои записи»); нужна, когда ролей недостаточно и правила зависят от данных.

**Policy-based authorization** — это механизм ASP.NET Core, где правила доступа оформляются именованными политиками; нужен, чтобы описывать сложные условия отдельно от кода эндпоинтов.

**ASP.NET Core Identity** — это встроенная система пользователей, ролей, паролей и токенов с хранением в БД; нужна, чтобы не писать регистрацию и управление учётками с нуля.

**OAuth 2.0** — это протокол делегированного доступа: приложение получает токен на ограниченные действия от имени пользователя, не зная его пароль; нужен для входа и доступа к API через внешних провайдеров.

**OpenID Connect (OIDC)** — это надстройка над OAuth 2.0, добавляющая аутентификацию и стандартный ID-токен; нужен, чтобы получать от провайдера сведения о том, кто вошёл.

**SSO (Single Sign-On)** — это единый вход: пользователь логинится один раз и получает доступ ко многим приложениям; нужен в системах с несколькими сервисами и корпоративным входом.

**Keycloak** — это готовый сервер идентификации с OAuth 2.0, OIDC, SSO и управлением пользователями; нужен, чтобы не писать собственный сервер авторизации.

## Взаимодействие с фронтендом

**CORS (Cross-Origin Resource Sharing)** — это механизм браузера, блокирующий запросы страницы к другому домену или порту, пока сервер явно не разрешит; нужен для безопасности, а настраивать его приходится, когда React на `localhost:5173` ходит в API на другом порту.

**HTTP-заголовки** — это служебные пары «имя: значение» в запросе и ответе (`Content-Type`, `Authorization`, `Cache-Control`); нужны для передачи формата данных, токена, правил кэширования и прочих метаданных.

**Cookie** — это небольшие данные, которые браузер хранит и автоматически шлёт на сервер; нужны для сессий и токенов, а флаги `HttpOnly`, `Secure`, `SameSite` защищают их от кражи и подделки запросов.

**HTTPS и TLS** — это шифрование HTTP-трафика и проверка подлинности сервера по сертификату; нужны, чтобы данные и токены нельзя было перехватить по дороге.

**Reverse proxy** — это сервер перед приложением, принимающий запросы и пересылающий их внутрь; нужен для TLS, балансировки, раздачи статики и сокрытия внутренней структуры.

**NGINX** — это веб-сервер и reverse proxy; нужен, чтобы отдавать фронтенд (статику React), проксировать запросы `/api` на бэкенд, терминировать HTTPS и распределять нагрузку.

**OpenAPI-контракт и генерация клиента** — по описанию API можно автоматически создать типизированный клиент для фронтенда (TypeScript); нужен, чтобы фронт и бэк не расходились в формате данных и не писать запросы вручную.

**Пагинация, фильтрация, сортировка** — это способы отдавать большие списки частями и по условиям (`?page=2&status=Watched`); нужны, чтобы не гонять по сети и не грузить в память всю таблицу.

**Версионирование API** — это способ выпускать новые версии контракта (`/v2/movies`), не ломая старых клиентов; нужно, когда у API несколько потребителей и менять формат «как удобно» нельзя.

## ElasticSearch, MongoDb, ClickHouse

**NoSQL** — это общее название баз, не использующих классическую реляционную модель (документные, колоночные, ключ-значение, графовые); нужны там, где реляционная БД неудобна: гибкая схема, поиск, огромные объёмы, аналитика.

**ElasticSearch** — это поисковый движок на инвертированном индексе: ищет по тексту с учётом морфологии, опечаток и релевантности и быстро агрегирует данные; нужен для полнотекстового поиска, а также для хранения и анализа логов. Для небольшого проекта обычно хватает полнотекстового поиска PostgreSQL.

**Полнотекстовый поиск PostgreSQL (FTS)** — это встроенный в Postgres поиск по словам с поддержкой словоформ и ранжирования; нужен как простая альтернатива ElasticSearch без отдельного сервиса.

**MongoDb** — это документная БД, хранящая данные как JSON-подобные документы без жёсткой схемы; нужна для данных с изменчивой структурой, когда документ удобнее читать и писать целиком.

**ClickHouse** — это колоночная СУБД для аналитики: быстро агрегирует миллиарды строк; нужна для отчётов, метрик и событий, а не для обычных транзакций.

**OLTP и OLAP** — OLTP это множество коротких транзакций (регистрация, оценка фильма), OLAP это тяжёлые аналитические запросы по большим данным; нужно различать, чтобы не нагружать боевую БД отчётами и выбирать подходящее хранилище.

## Тестирование

**Юнит-тест** — это проверка одной небольшой единицы логики (метода, класса) в изоляции от БД, сети и файлов; нужен, чтобы быстро ловить ошибки в бизнес-правилах и безопасно рефакторить.

**Интеграционный тест** — это проверка нескольких частей вместе (API + EF Core + настоящая БД); нужен, чтобы убедиться, что компоненты стыкуются: запросы, миграции, сериализация, DI.

**E2E-тест** — это проверка всего сценария «снаружи», как это делает пользователь (через браузер или HTTP); нужен для контроля критичных пользовательских путей, но он самый медленный и хрупкий.

**Пирамида тестов** — это ориентир по пропорциям: много быстрых юнит-тестов, меньше интеграционных, совсем немного E2E; нужна, чтобы тесты оставались быстрыми и поддерживаемыми.

**Arrange-Act-Assert (AAA)** — это структура теста из трёх частей: подготовка, действие, проверка; нужна, чтобы тесты читались одинаково и было видно, что именно проверяется.

**xUnit** — это основная библиотека для написания и запуска тестов в .NET (`[Fact]`, `[Theory]`); нужна как базовый фреймворк, на котором строится всё остальное тестирование.

**Mock, Stub, Fake (test doubles)** — это подставные объекты вместо настоящих зависимостей: stub возвращает заготовленные данные, mock ещё и проверяет, как его вызывали, fake — упрощённая рабочая реализация; нужны, чтобы изолировать тестируемый код.

**Moq и NSubstitute** — это библиотеки, которые создают моки интерфейсов на лету; нужны, чтобы не писать подставные классы руками и настраивать их поведение прямо в тесте.

**AutoFixture** — это генератор случайных тестовых данных для объектов; нужен, чтобы не заполнять вручную десятки полей и не завязывать тест на лишние значения.

**FluentAssertions** — это библиотека читаемых проверок (`result.Should().Be(5)`) с понятными сообщениями об ошибках; нужна для удобства чтения тестов. У новых версий условия лицензии стоит проверить, альтернативы — Shouldly и форк AwesomeAssertions.

**WebApplicationFactory** — это класс, который поднимает приложение ASP.NET Core в памяти внутри теста; нужен для интеграционных тестов API без реального сервера.

**Testcontainers** — это библиотека, которая в тесте сама запускает Docker-контейнер (например, PostgreSQL) и убирает его после; нужна, чтобы интеграционные тесты шли на настоящей БД, а не на подделке.

**Respawn** — это библиотека, которая быстро очищает данные в БД между тестами; нужна, чтобы тесты не влияли друг на друга и не приходилось каждый раз пересоздавать базу.

**TDD (Test-Driven Development)** — это практика, где сначала пишется падающий тест, потом код, который его проходит; нужна, чтобы заранее продумать поведение и держать код тестируемым.

## Фоновые процессы

**Фоновая задача** — это работа, которая выполняется вне HTTP-запроса: письма, отчёты, обработка файлов, синхронизация; нужна, чтобы не заставлять пользователя ждать и не держать запрос открытым.

**IHostedService** — это интерфейс ASP.NET Core для кода, который запускается и останавливается вместе с приложением; нужен как базовая точка входа для любых долгоживущих фоновых компонентов.

**BackgroundService** — это готовый базовый класс над `IHostedService` с одним методом `ExecuteAsync`, где крутится цикл работы; нужен для простых фоновых воркеров: опрос очереди, периодическая очистка.

**Producer/Consumer** — это схема, где одни части кода кладут задачи в очередь, а другие их разбирают; нужна, чтобы развязать приём работы и её выполнение и сгладить пики нагрузки.

**Channels (`System.Threading.Channels`)** — это потокобезопасная очередь внутри процесса с асинхронным чтением и записью; нужна для реализации producer/consumer в памяти приложения без внешних брокеров.

**Cron-выражение** — это запись расписания в виде пяти-шести полей (минуты, часы, дни); нужно, чтобы задавать «каждый день в 03:00» или «каждые 5 минут».

**Quartz.NET** — это библиотека планировщика с триггерами, cron-расписаниями, группами задач и хранением состояния в БД; нужна, когда важны точное расписание и надёжный запуск периодических задач.

**Hangfire** — это библиотека фоновых задач с хранением в БД и готовой панелью мониторинга: умеет немедленные, отложенные и периодические задачи с автоматическими повторами; нужна, когда нужно быстро получить надёжную очередь задач и видеть их состояние.

**Retry и идемпотентность** — retry это повторная попытка после сбоя, идемпотентность это свойство операции давать один результат при повторном выполнении; нужны вместе, чтобы повтор задачи не создавал дублей (двойное письмо, двойное списание).

## WebSockets и SignalR

**Real-time взаимодействие** — это обмен данными, где сервер сам отправляет обновления клиенту без повторных запросов; нужен для чатов, уведомлений, живых статусов и прогресса долгих операций.

**Polling и Long polling** — polling это когда клиент регулярно спрашивает сервер «есть новое?», long polling — когда сервер держит запрос открытым до появления данных; нужны как простой запасной способ, но создают лишнюю нагрузку.

**WebSockets** — это протокол постоянного двустороннего соединения между браузером и сервером поверх одного TCP-подключения; нужен для быстрого обмена сообщениями в обе стороны без накладных расходов на каждый запрос.

**Server-Sent Events (SSE)** — это односторонний поток событий от сервера к браузеру по обычному HTTP; нужен, когда достаточно только присылать обновления (лента, прогресс), без ответов от клиента.

**SignalR** — это библиотека ASP.NET Core над WebSockets (с автоматическим откатом на SSE и long polling), которая даёт готовую модель: клиенты вызывают методы сервера, а сервер вызывает методы клиентов; нужна, чтобы не писать протокол соединения и переподключения вручную.

**Hub, группы и клиенты** — hub это серверный класс SignalR с методами, которые вызывают клиенты; группы позволяют рассылать сообщения подмножеству подключённых; нужны, чтобы адресовать уведомления конкретному пользователю или комнате.

**Backplane (Redis)** — это общий канал между экземплярами приложения, через который SignalR пересылает сообщения; нужен при нескольких инстансах сервера, иначе клиент, подключённый к одному из них, не получит сообщение, отправленное с другого.

## Работа с файлами

**Файловое и объектное хранилище** — файловое хранит данные в папках на диске сервера, объектное хранит файлы как объекты с ключом и метаданными через HTTP API; нужно, чтобы не копить пользовательские файлы на диске приложения и не терять их при его перезапуске или масштабировании.

**S3** — это объектное хранилище Amazon и одновременно стандарт API, который повторяют многие хранилища; нужно для надёжного хранения картинок, видео, документов и бэкапов с доступом по ключу.

**MinIO** — это бесплатное S3-совместимое хранилище, которое можно поднять у себя (например, в Docker); нужно, чтобы разрабатывать и тестировать работу с S3 локально, не платя за облако.

**Bucket, object, key** — bucket это «корзина» верхнего уровня, object это сам файл, key это его уникальное имя (путь) внутри корзины; нужны, чтобы понимать модель адресации в S3 — там нет настоящих папок, только префиксы ключей.

**Presigned URL** — это временная подписанная ссылка на загрузку или скачивание конкретного объекта в хранилище; нужна, чтобы клиент передавал файл напрямую в S3, не нагружая бэкенд, и при этом без постоянных ключей доступа на фронтенде.

**Multipart upload** — это загрузка большого файла по частям, которые отправляются независимо и собираются хранилищем; нужна для гигабайтных файлов: можно повторить упавшую часть и грузить параллельно.

**Загрузка через API: `IFormFile` и стриминг** — `IFormFile` принимает файл из формы, а потоковая обработка читает его кусками без загрузки целиком в память; нужны для простых загрузок, но для больших файлов надёжнее presigned URL.

**Метаданные файла в БД** — это запись о файле (ключ в хранилище, имя, размер, тип, владелец), которая хранится в базе, а сам файл лежит в хранилище; нужна, чтобы искать и фильтровать файлы и проверять права, не обращаясь к хранилищу.

**Content-Type (MIME-тип)** — это обозначение формата файла в HTTP (`image/png`, `application/pdf`); нужно, чтобы браузер правильно показывал файл, а сервер мог проверять допустимые типы при загрузке.

**CDN** — это сеть серверов по миру, которая кэширует файлы рядом с пользователем; нужна, чтобы отдавать статику и медиа быстро и снять нагрузку с основного хранилища.

## Обработка файлов

**FFmpeg** — это консольная утилита для работы с аудио и видео: конвертация форматов, нарезка, сжатие, извлечение кадров; нужна, когда приложение принимает видео или аудио и должно привести их к нужному формату, сделать превью или подготовить к стримингу.

**ZIP и RAR (архивы)** — это форматы упаковки нескольких файлов в один со сжатием; в .NET ZIP поддерживается встроенно (`System.IO.Compression`), для RAR нужны сторонние библиотеки; нужны для выгрузки набора файлов одним архивом и для распаковки загруженных пользователем.

**QuestPDF** — это библиотека генерации PDF из кода на C# в декларативном стиле (макет описывается как дерево элементов); нужна для счетов, отчётов и выгрузок с аккуратной вёрсткой. Условия лицензии для коммерческого использования стоит проверить.

**PdfSharp** — это библиотека для создания и правки PDF более низкого уровня (рисование на странице, объединение документов); нужна, когда надо работать с уже готовыми PDF или рисовать документ вручную.

**EPPlus** — это библиотека чтения и записи Excel-файлов (`.xlsx`) с богатыми возможностями (формулы, диаграммы, стили); нужна для сложных Excel-отчётов. В последних версиях лицензия ограничивает коммерческое использование — стоит проверить.

**ClosedXML** — это бесплатная библиотека работы с Excel (`.xlsx`) с простым API поверх Open XML; нужна для типичных выгрузок и импортов таблиц без лицензионных ограничений.

**Импорт и экспорт данных (CSV, Excel)** — это загрузка данных из файлов в систему и выгрузка из неё; нужны, чтобы пользователи могли переносить данные массово, а система проверяла и отсеивала некорректные строки.

## Брокеры сообщений

**Брокер сообщений** — это посредник между сервисами: один кладёт сообщение, другой забирает его позже и независимо; нужен, чтобы сервисы не зависели от доступности друг друга в момент вызова и чтобы сглаживать пики нагрузки.

**Очередь, topic и pub/sub** — очередь доставляет каждое сообщение одному получателю, topic с моделью pub/sub доставляет копию каждому подписчику; нужны, чтобы выбирать между «разобрать задачу» и «оповестить всех заинтересованных».

**RabbitMQ** — это брокер сообщений на основе очередей: издатель шлёт сообщение в exchange, тот по правилам маршрутизации (routing key) раскладывает его по очередям, потребитель подтверждает обработку (ack); нужен для задач, команд и гибкой маршрутизации с гарантиями доставки.

**Kafka** — это распределённый журнал событий: сообщения дописываются в topic, делённый на partition, и хранятся заданное время, а потребители читают с нужной позиции (offset) в составе consumer group; нужна для больших потоков событий, перечитывания истории и аналитики.

**RabbitMQ и Kafka: в чём разница** — RabbitMQ удаляет сообщение после обработки и сильнее в маршрутизации, Kafka хранит журнал и сильнее в объёме и повторном чтении; нужно знать, чтобы выбирать инструмент под задачу, а не по моде.

**MassTransit** — это библиотека-обёртка над брокерами для .NET: берёт на себя подключение, сериализацию, повторы и маршрутизацию; нужна, чтобы работать с RabbitMQ и другими брокерами через единый удобный API. Условия лицензии новых версий стоит проверить.

**Event-driven архитектура** — это подход, где сервисы общаются событиями («фильм оценён») вместо прямых вызовов; нужен для слабой связности: источник события не знает, кто на него реагирует.

**Событие и команда** — событие говорит о случившемся факте и адресовано всем желающим, команда просит выполнить конкретное действие и адресована одному получателю; нужно различать, чтобы правильно выбирать способ доставки и владельца логики.

**Outbox** — это паттерн: сообщение сначала записывается в таблицу той же БД и той же транзакцией, что и бизнес-данные, а отдельный процесс затем отправляет его в брокер; нужен, чтобы не потерять сообщение и не отправить его, если транзакция откатилась.

**Inbox и идемпотентный потребитель** — потребитель запоминает идентификаторы обработанных сообщений и пропускает повторы; нужен, потому что брокеры гарантируют «как минимум один раз», и дубликаты неизбежны.

**DLQ (Dead Letter Queue)** — это отдельная очередь для сообщений, которые не удалось обработать после нескольких попыток; нужна, чтобы «ядовитое» сообщение не блокировало поток, а его можно было разобрать вручную.

**Eventual consistency (итоговая согласованность)** — это модель, при которой данные в разных сервисах расходятся на короткое время и затем приходят к согласованному виду; нужна понимать, потому что при асинхронном обмене мгновенной согласованности не бывает.

## Микросервисы

**Микросервисная архитектура** — это подход, где система состоит из небольших независимо разворачиваемых сервисов, каждый со своей зоной ответственности и данными; нужна, когда большим командам и разным частям системы нужно развиваться и масштабироваться независимо. Цена — сложность сети, данных и эксплуатации, поэтому для маленького проекта она не нужна.

**Распределённый монолит** — это антипаттерн: сервисы формально разделены, но так связаны между собой, что менять и выкладывать их можно только вместе; нужно знать, чтобы не получить все минусы микросервисов без плюсов.

**Синхронное и асинхронное взаимодействие** — синхронное означает «вызвал и жду ответ» (HTTP, gRPC), асинхронное означает «отправил сообщение и пошёл дальше» (брокер); нужно выбирать осознанно: синхронное проще, асинхронное устойчивее к сбоям.

**gRPC** — это протокол вызова удалённых методов поверх HTTP/2 с бинарной сериализацией; нужен для быстрого типизированного общения между внутренними сервисами, где важны скорость и строгий контракт.

**Protobuf (Protocol Buffers)** — это компактный бинарный формат описания и передачи данных со схемой в `.proto`-файлах; нужен как язык контрактов gRPC и для генерации клиентов и серверов.

**Vertical Slice Architecture** — это организация кода не по техническим слоям, а по функциям: всё для одного сценария (запрос, обработчик, валидация, доступ к данным) лежит рядом; нужна, чтобы изменение одной фичи не размазывалось по пяти проектам. Это альтернатива слоистой Clean Architecture.

**Контракт сервиса и совместимость** — контракт это описание того, что сервис принимает и возвращает; нужна обратная совместимость, чтобы изменение одного сервиса не ломало остальных.

## Паттерны микросервисов

**API Gateway** — это единая точка входа для клиентов, которая маршрутизирует запросы к нужным сервисам и берёт на себя общие задачи (аутентификация, лимиты, логирование); нужен, чтобы клиент не знал о внутренней структуре сервисов. В .NET для этого используют YARP.

**BFF (Backend For Frontend)** — это отдельный бэкенд под конкретный клиент (веб, мобильное приложение), который собирает данные из нескольких сервисов в удобный ему вид; нужен, чтобы каждый клиент получал ровно то, что ему нужно, без лишних запросов.

**Service Discovery** — это механизм, по которому сервисы находят адреса друг друга, когда те меняются; нужен, потому что в контейнерах и кластерах адреса не фиксированы.

**Health checks** — это эндпоинты, сообщающие, жив ли сервис и готов ли принимать трафик; нужны оркестратору и балансировщику, чтобы убирать неисправные экземпляры из обработки.

**Retry и Polly** — retry это повтор неудавшегося вызова, обычно с нарастающей задержкой, Polly — библиотека .NET, которая реализует retry, timeout, circuit breaker и другие политики устойчивости; нужны, чтобы кратковременные сбои сети не превращались в ошибки для пользователя.

**Circuit Breaker** — это «предохранитель»: после серии неудачных вызовов к сервису вызовы временно прекращаются и сразу возвращают ошибку; нужен, чтобы упавший сервис не тянул за собой остальные и получил время восстановиться.

**Timeout** — это ограничение времени ожидания ответа; нужен, чтобы зависший сервис не держал потоки и соединения бесконечно.

**Rate limiting** — это ограничение числа запросов от клиента за период времени; нужно для защиты от перегрузки и злоупотреблений; в ASP.NET Core есть встроенный middleware.

**Database per Service** — это принцип: у каждого сервиса своя база, и чужие данные берутся только через его API или события; нужен для независимости сервисов, но лишает возможности делать JOIN между сервисами.

**Saga** — это способ провести бизнес-операцию через несколько сервисов цепочкой локальных транзакций, а при сбое выполнить компенсирующие действия (оркестрация — центральный координатор, хореография — сервисы реагируют на события друг друга); нужна, потому что распределённой ACID-транзакции между сервисами нет.

**Event Sourcing** — это подход, при котором хранятся не текущие значения, а последовательность событий, из которых состояние восстанавливается; нужен для полной истории изменений и аудита, но сильно усложняет систему, поэтому в учебном проекте он в бэклоге.

**Distributed tracing (распределённая трассировка)** — это сквозное отслеживание одного запроса через все сервисы с идентификатором трассы; нужна, чтобы видеть, где именно запрос тормозит или падает (OpenTelemetry, Jaeger — в разделе о мониторинге).

## DDD (Domain-Driven Design)

**DDD** — это подход к проектированию сложных систем, где в центре модель предметной области и язык бизнеса, а не таблицы и технологии; нужен, чтобы сложную бизнес-логику можно было разделить на понятные части и общаться о ней с бизнесом на одном языке.

**Ubiquitous Language (единый язык)** — это общий словарь терминов, которым пользуются и бизнес, и разработчики, и код; нужен, чтобы названия в коде совпадали с тем, как объясняет процесс предметный эксперт, а непонимание не рождало ошибки.

**Bounded Context (ограниченный контекст)** — это граница, внутри которой термины и модель имеют одно определённое значение («Пользователь» в авторизации и в каталоге фильмов — разные модели); нужен, чтобы не строить одну раздувшуюся модель на всё и проводить чёткие границы модулей. Решения о границах — за тобой.

**Subdomain (core, supporting, generic)** — это деление предметной области по важности: core — то, что даёт продукту преимущество, supporting — нужное, но не уникальное, generic — типовое (авторизация, платежи); нужно, чтобы вложить основные усилия в core, а типовое взять готовым.

**Value Object** — это неизменяемый объект без собственной идентичности, который сравнивается по значению (денежная сумма, диапазон дат, рейтинг от 1 до 10); нужен, чтобы зашить правила прямо в тип и не передавать голые `int` и `string` по всей системе. В C# удобно описывается через `record`.

**Aggregate и Aggregate Root** — агрегат это группа связанных объектов, которые меняются как единое целое, а aggregate root — единственная точка входа в неё снаружи; нужны, чтобы определить границу транзакции и защитить инварианты всей группы.

**Domain Event** — это объект, описывающий важный факт, уже произошедший в домене («фильм оценён», «статус изменён»); нужен, чтобы другие части системы могли на него реагировать, не будучи жёстко связанными с источником.

**Domain Service** — это бизнес-логика, которая не принадлежит ни одной сущности по её природе (работает с несколькими объектами); нужен, чтобы не засовывать такую логику в неподходящую сущность и не выносить её в инфраструктуру.

**Anti-Corruption Layer (ACL)** — это прослойка-переводчик между вашей моделью и чужой (внешний API, устаревшая система); нужен, чтобы чужие термины и структуры не протекали внутрь вашего домена (например, ответ стороннего API каталога фильмов).

**Context Map** — это схема взаимосвязей между bounded context’ами: кто от кого зависит и как они обмениваются данными; нужна, чтобы видеть целую картину и планировать интеграцию модулей или сервисов.

## Мониторинг и наблюдаемость

**Observability (наблюдаемость)** — это способность понять внутреннее состояние системы по трём сигналам: логам, метрикам и трассировкам; нужна, чтобы увидеть проблему раньше пользователя и найти её причину.

**Метрики** — это числовые показатели во времени (число запросов в секунду, доля ошибок, время ответа, загрузка CPU); нужны, чтобы видеть общее здоровье системы и тренды.

**Trace и span** — trace это путь одного запроса через систему, span — один шаг внутри него со временем начала и длительностью (вызов БД, вызов другого сервиса); нужны, чтобы видеть, где именно теряется время.

**OpenTelemetry** — это стандарт и набор библиотек для сбора метрик, трассировок и логов в едином формате; нужен, чтобы инструментировать приложение один раз и потом отправлять данные в любой из совместимых систем.

**Prometheus** — это система сбора и хранения метрик, которая сама периодически опрашивает сервисы и даёт язык запросов PromQL; нужна как база метрик для графиков и алертов.

**Grafana** — это веб-интерфейс для дашбордов и графиков, который рисует данные из Prometheus и других источников; нужна, чтобы наглядно наблюдать за системой и настраивать оповещения.

**Jaeger** — это система хранения и просмотра распределённых трассировок; нужна, чтобы видеть путь запроса через сервисы как диаграмму с временем каждого шага.

**Kibana** — это веб-интерфейс Elastic Stack для поиска и визуализации данных из Elasticsearch, особенно логов; нужна, чтобы искать и анализировать логи нескольких сервисов в одном месте.

**Alerting (алерты)** — это автоматическое уведомление, когда метрика вышла за допустимые пределы (много ошибок, сервис не отвечает); нужны, чтобы узнавать о сбое от системы, а не от пользователей.

## Frontend

**React** — это библиотека для построения интерфейсов из компонентов, которая обновляет страницу при изменении состояния; нужен, чтобы дать бэкенду реальный клиент и понимать, как его API использует фронтенд (в проекте клиент лежит в `client/`).

**TypeScript** — это JavaScript со статической типизацией: типы проверяются до запуска; нужен, чтобы ловить ошибки на этапе написания и описывать контракт данных бэкенда (DTO) на фронтенде.

**SPA (Single Page Application)** — это одностраничное приложение, которое загружается один раз и дальше обменивается с сервером только данными через API; нужно для быстрого интерфейса без полной перезагрузки страницы.

**Компоненты, props и state** — компонент это функция, возвращающая часть интерфейса, props — данные, передаваемые в неё сверху, state — её собственное меняющееся состояние; нужны, чтобы собирать интерфейс из переиспользуемых блоков.

**Hooks (`useState`, `useEffect`)** — это функции React, которые подключают к компоненту состояние и побочные эффекты (запрос к API, подписка); нужны для загрузки данных и реакции на действия пользователя.

**Vite и npm** — npm это менеджер пакетов JavaScript (аналог NuGet), Vite — инструмент сборки и быстрый dev-сервер; нужны, чтобы устанавливать библиотеки, запускать фронт локально и собирать его для прода.

**fetch и axios** — это способы отправлять HTTP-запросы из браузера: `fetch` встроен в браузер, `axios` — библиотека с удобными надстройками; нужны, чтобы фронтенд обращался к API бэкенда.

**TanStack Query (React Query)** — это библиотека управления серверными данными на фронте: кэширует ответы, повторяет запросы, следит за состоянием загрузки и ошибок; нужна, чтобы не писать эту логику руками через `useEffect`.

**React Router** — это библиотека маршрутизации в SPA: сопоставляет URL в браузере с компонентами-страницами без перезагрузки; нужна, чтобы у приложения были адреса страниц, работала кнопка «назад» и прямые ссылки.

## Термины из видео, которых нет на схеме

**SOLID** — это пять принципов объектно-ориентированного проектирования: одна ответственность на класс (S), расширение без правки старого кода (O), возможность подставлять наследника вместо базового типа (L), маленькие узкие интерфейсы (I), зависимость от абстракций, а не от конкретных классов (D); нужны как чек-лист, почему код становится хрупким и как его исправить.

**Cohesion и coupling (связность и зацепление)** — cohesion это насколько части одного модуля подходят друг к другу (желательно высокая), coupling — насколько модули зависят друг от друга (желательно низкое); нужны как критерий качества границ модулей.

**CQS (Command-Query Separation)** — это правило: метод либо меняет состояние, либо возвращает данные, но не то и другое одновременно; нужно для предсказуемости кода. CQRS — его расширение на уровень архитектуры.

**HLS (HTTP Live Streaming)** — это формат потокового видео: ролик нарезается на короткие сегменты с плейлистом `.m3u8`, и плеер подгружает их по мере просмотра, подбирая качество под скорость сети; нужен, чтобы не скачивать видео целиком перед просмотром. Сегменты обычно готовит FFmpeg.

**Эмбеддинги (embeddings)** — это числовые векторы, которые передают смысл текста или картинки: похожие по смыслу объекты дают близкие векторы; нужны для семантического поиска, рекомендаций и RAG. Хранить их можно в векторной БД или в PostgreSQL с расширением `pgvector`.

**Гибридный поиск** — это сочетание полнотекстового поиска (по словам) и векторного (по смыслу) с объединением результатов; нужен, чтобы слова находили точные совпадения, а векторы — похожие по смыслу записи, и поиск был точнее каждого по отдельности.

**RAG (Retrieval-Augmented Generation)** — это подход, при котором перед ответом языковой модели из ваших данных находятся релевантные фрагменты и подставляются в запрос; нужен, чтобы модель отвечала по актуальным и приватным данным и реже выдумывала.

**MCP (Model Context Protocol)** — это открытый протокол, по которому ИИ-модели и агенты подключаются к внешним инструментам и данным через стандартные серверы; нужен, чтобы дать агенту доступ к БД, API и файлам единым способом, а не писать интеграцию под каждый сервис.

**Spec-Driven Development** — это подход к разработке с ИИ-агентами, где сначала пишется подробная спецификация (что и как должно работать), а агент реализует её и пишет тесты; нужен, чтобы управлять результатом и понимать код, а не генерировать его наудачу. По сути это то, как устроен текущий режим работы над проектом.

**SSR и Next.js** — SSR (server-side rendering) это рендеринг страницы в HTML на сервере, Next.js — фреймворк на React с поддержкой SSR и маршрутизации; нужны, когда важны SEO и быстрая первая отрисовка, в отличие от обычного SPA.

**Tailwind CSS** — это CSS-фреймворк с утилитарными классами (`flex`, `p-4`, `text-center`), которые пишутся прямо в разметке; нужен для быстрой вёрстки без отдельных CSS-файлов и сборки собственной системы стилей.

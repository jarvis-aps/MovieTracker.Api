# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Что это за проект

Учебный пет-проект: постепенный переход от Unity/C# к .NET backend-разработке. Трекер просмотренных фильмов на .NET 10 + EF Core + PostgreSQL, растущий по четырём независимым осям (данные, бэкенд, фронт, инфраструктура) — см. `PROJECT_BRIEF.md`.

**Перед тем как что-либо делать в этом репозитории — прочитай `PROJECT_BRIEF.md` целиком.** Там актуальный статус, текущая задача этапа и дорожная карта. Этот файл (`CLAUDE.md`) её не дублирует, потому что статус меняется после каждой закрытой задачи, а `PROJECT_BRIEF.md` — единственный источник истины по прогрессу.

## Режим работы агента — обязательно к соблюдению

Проект учебный: цель — понимание, а не только рабочий код. Режим работы изменён 2026-10-05 по решению пользователя; подробности — в разделе «Режим работы агента» в `PROJECT_BRIEF.md`, при расхождениях он первичен.

- **Пользователь проектирует и принимает решения, агент реализует и объясняет.** Агент пишет код, миграции, DTO, CRUD и тесты по принятому дизайну и сам проверяет результат: сборка, тесты, curl/psql, логи.
- **Решает только пользователь, на любом этапе:** границы модулей / что уходит в событие vs прямой вызов, дизайн модели данных, дизайн запросов и их сложность. Агент излагает варианты с компромиссами и ждёт выбора; без него реализация не начинается и по инициативе агента не расширяется.
- Задачи выдаются **по одной**, в формате из `PROJECT_BRIEF.md` (раздел «Формат выдачи задачи», с полем «Решаешь ты»). Один небольшой diff на задачу, без лишних правок.
- К каждому нетривиальному решению — объяснение «почему так, а не иначе»: альтернатива и компромисс, а не пересказ кода.
- После реализации агент задаёт вопросы по коду, пользователь отвечает своими словами. Задача не закрыта, пока ключевые решения не объяснены. Вайб-кодинг без понимания не допускается.
- После закрытия задачи — обнови раздел «Текущий статус» в `PROJECT_BRIEF.md` (что сделано, что уточнилось по факту, следующая задача) и отметь чек-лист.
- Режим пробный. Вернуть строгий (агент не пишет реализацию, только выдаёт задачу и проверяет) можно явным сообщением пользователя.

Прежде чем начинать задачу по бизнес-логике — свериться, на каком этапе находится работа (раздел «Текущий статус» в `PROJECT_BRIEF.md`).

## Команды

Проект лежит плоско в корне репозитория (без `.sln`, один `.csproj`).

```bash
dotnet build                    # сборка
dotnet run                      # запуск (http://localhost:5066, https://localhost:7131)
dotnet watch run                # запуск с hot reload
```

### Тесты

`MovieTracker.Api.Tests` (xUnit + Testcontainers, задача 3.6): сервисы проверяются против настоящего Postgres 17, который тест сам поднимает в отдельном контейнере на случайном порту — `movietracker-db` и порт 5432 не затрагиваются. **OrbStack должен быть запущен** (включает пользователь, агент его не запускает).

```bash
dotnet test MovieTracker.Api.Tests    # весь набор, ~10 с вместе со сборкой
```

`.sln` нет намеренно: рядом с `.csproj` в корне он сломал бы `dotnet build` («в папке несколько файлов проекта»), поэтому тесты запускаются по пути проекта. Основной `.csproj` исключает подпапку тестов из своей компиляции (`DefaultItemExcludes`) — иначе плоская раскладка втянула бы её файлы в приложение.

### EF Core миграции

`dotnet-ef` установлен как global tool (`~/.dotnet/tools`, в PATH).

```bash
dotnet ef migrations add <Name>     # новая миграция
dotnet ef database update           # применить миграции к БД
dotnet ef migrations remove         # откатить последнюю неприменённую миграцию
```

### База данных

PostgreSQL 17 в контейнере `movietracker-db` (порт 5432). Контейнеры здесь работают под **OrbStack**, а не под Docker Desktop: команды `docker ...` те же (OrbStack Docker-совместим), но демоном служит OrbStack, и пользователь включает его сам — агент его не запускает (если демон недоступен, попросить включить). Строка подключения — в `appsettings.Development.json` (ключ `ConnectionStrings:MovieTrackerDb`), пароль учебный/локальный.

```bash
docker exec -it movietracker-db psql -U movietracker -d movietracker
# внутри psql: \d "Movies"   — кавычки обязательны, EF Core создаёт таблицы с регистром как у C#-класса,
# Postgres по умолчанию сворачивает нижний регистр
```

## Архитектура

Этап 1 закрыт, этап 3 в работе (см. `PROJECT_BRIEF.md`). Структура бэкенда:

```
Initializer/         # Bootstrap.cs (бывший Program.cs, переименован и перенесён пользователем в задаче 3.2 — "всё для запуска приложения в одном месте") — точка входа + все Minimal API endpoints инлайн, без Main-класса; MovieTrackerDbContext.cs — DbContext, лежит здесь же по той же идее, не в отдельной Data/
Models/               # сущности (Movie, Genre, User, UserMovieData), enum'ы (Status, SortBy), DTO (MovieDto, GenreDto, MoviesPage — страница каталога с totalCount)
Seeders/              # GenresSeeder, MovieSeeder, UsersSeeder, UserMovieDataSeeder — все IAsyncInitializer; порядок регистрации в Bootstrap.cs важен — каждый следующий зависит по FK от данных предыдущих
Services/             # WatchlistService — бизнес-логика, без HTTP-семантики; IWatchlistReader — единственный способ для handler'а каталога (GetMoviesHandler) узнать про watchlist (таблицу WatchlistItems он напрямую не читает, 3.7); личные данные для списка handler каталога пока читает сам (m.MoviesData) — чтение отдельной задачей. Прежние сервисы MovieService (в 3.19) и UserMovieDataService (в 3.18) удалены: их логика переехала в handler'ы Commands/ и Queries/
Exceptions/           # кастомные исключения для доменной валидации (InvalidRatingException, InvalidPageSizeException, InvalidNotesException)
Mediator/             # свой мини-mediator (3.14, не MediatR): IMediator/DefaultMediator, IRequest, IRequestHandler, IPipelineBehavior, TimingBehavior (замер времени), AddMediator (сканирует сборку на handler'ы)
Commands/             # команды CQRS и их handler'ы (SetStatusCommand, SetNotesCommand, SetRatingCommand, 3.14 и 3.16; CreateMovieCommand для POST /movies, 3.19: плоская неизменяемая запись из трёх полей, биндится прямо из тела запроса; дубликат фильма — пара (название, год), её уникальность гарантирует индекс IX_Movies_Title_Year, handler ловит нарушение и отвечает null, то есть 400, 3.20); логика операций (проверка существования, границы заметки и оценки) живёт в самих handler'ах, общая механика записи (найти или создать запись пары, сохранить с повтором при гонке первого PATCH) — в UserMovieDataWriter, который handler'ы получают через DI (3.18); UserMovieDataService удалён
Queries/              # запросы CQRS и их handler'ы (GetMoviesQuery/GetMoviesHandler, 3.15); запрос — неизменяемая запись, дефолты page/pageSize лежат в ней и биндятся через [AsParameters] прямо из query-строки; вся логика запроса (фильтры, сортировки, границы страницы, totalCount, личный вид пользователя) живёт в самом GetMoviesHandler (3.19)
Migrations/           # генерируется EF Core, руками не редактировать
client/               # React + TypeScript + Vite, отдельный фронтенд-проект
MovieTracker.Api.Tests/  # xUnit + Testcontainers: тесты сервисов против Postgres в контейнере (3.6); отдельный проект, в компиляцию приложения не входит
```

Namespace'ы соответствуют папкам (`MovieTracker.Api.Models`, `MovieTracker.Api.Initializer`, `MovieTracker.Api.Seeders`) — стандартная C#-конвенция, Rider иначе подсвечивает warning. Эндпоинты (`MapGet`/`MapPatch`/`MapPost`) остаются инлайн в `Bootstrap.cs`, **намеренно** не растащены на `Endpoints/`/`Controllers/` — это уже следующий уровень структуры, вводить его сейчас значило бы architecture без повода.

Архитектура **осознанно не вводится заранее** — это прямое правило проекта («Философия проекта» в `PROJECT_BRIEF.md`): слои, CQRS, mediator-паттерн, модульность появляются только с реальным поводом (вторая сущность, вторая связь, реальная бизнес-логика), а не потому что «так принято». Не предлагай и не добавляй эти слои преждевременно, даже если это выглядит как «best practice» — на этапе 1 это осознанный анти-паттерн для целей проекта. **Исключение с этапа 3 (решение пользователя 2026-11-10):** CQRS, mediator и события вводятся осознанно «для наглядности», даже без повода по нагрузке; не возражай «повода нет», объясняй цену и риск приёма (подробности в «Философии проекта» в `PROJECT_BRIEF.md`).

Плановая траектория усложнения (полная таблица — в `PROJECT_BRIEF.md`, раздел «Дорожная карта»):

| Этап | Бэкенд |
|---|---|
| 1. MVP (сейчас) | Один проект, Minimal API, `DbContext` напрямую в хендлере, без слоёв и mediator |
| 2 | Service-слой + DTO отдельно от EF-сущностей |
| 3 | Модульный монолит (Movies/Users/Lists), CQRS, свой мини-mediator (~20-30 строк, не MediatR — тот перешёл на коммерческую лицензию в 2025) или MediatR Community edition |
| 4 | Cross-cutting: валидация, auth, логирование |
| 5 (опционально) | Hosted background service, вынос модуля в отдельный сервис |

Стек: .NET 10, EF Core 10 (`Microsoft.EntityFrameworkCore.Design`), `Npgsql.EntityFrameworkCore.PostgreSQL`, PostgreSQL. Фронт (React + TypeScript, без стейт-менеджера на этапе 1) появится начиная с задачи 1.5 — отдельного фронтенд-проекта в репозитории пока нет.
